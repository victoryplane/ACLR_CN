# 05 · 打包与 ISO：把改好的文件装配成可启动镜像

## 背景与目标

前面几篇完成了「解包 → 翻译 → 字库 → 回写」，最终得到的是一堆改过的数据：更大的字库、
变长的文本容器、补丁后的菜单文件等。本篇解决最后一步：**如何把这些改动安全地放回 ISO，
生成一个模拟器能启动、游戏能正常读的镜像**。

这一层的核心不是「把字节写进去」，而是三件事：

1. 理解 ISO9660 里**文件落点（LBA/extent）与长度（size）的语义**，改动后同步更新；
2. 理解游戏对**高位偏移、扇区对齐**等约束，落点不能只图省事；
3. 建立**落点验证**的纪律——用文件表验证，而不是靠眼睛看「这里好像是空的」。

本篇所有十六进制值（LBA、offset、魔数）均来自对 ACLR（PS2）原版镜像与汉化镜像的实际测量，
可直接作为同结构镜像的参考；但**每个游戏的具体值请以你自己的文件表为准**。

## 前置依赖

- **自备正版游戏 ISO**（本仓库不提供任何游戏文件），以及解包出来的、要改写的容器/文件；
- **Python 3.x**：标准库 `struct` / `io` / `hashlib` 即可完成大部分原位读写与校验；
- **ISO 工具（可选）**：`mkisofs` / `genisoimage` 可用于「提取后重建文件系统」的备选路线，
  但重建会改变所有文件的 LBA 布局，见下文风险提示；
- 一份**权威文件表**：从 ISO9660 目录树或解包工具导出的「每个文件 → 起始 LBA + 字节长度」。
  它是本篇所有落点判断的依据，没有它不要动手。

本文推荐的主路线是**原位 patch + 更新目录记录**（即直接对 ISO 文件做 `seek`/读写，
再改 ISO9660 目录里的 extent/size 字段），因为这条路线对 LBA 布局的扰动最小。

## ISO9660 速览

PS2 光盘常用 ISO9660 文件系统，逻辑扇区大小 **2048 字节**。一个 LBA 号 = 一个 2048 字节扇区，
文件在镜像里的字节偏移 = `LBA × 2048`。

### 3.1 从 PVD 找到根目录

- **Primary Volume Descriptor（PVD）**：位于 **LBA 16**（字节偏移 `16 × 2048`）。
  它的标识符是 `CD001`（出现在 PVD 内偏移 `+1` 起 5 字节）。
- PVD 内有一份「根目录记录」，指向根目录的 LBA 与大小。本项目实测：根目录记录起始于
  PVD 内偏移 `+0x9C`，其中根目录 LBA 的小端在 `+0x9C + 2`，根目录大小的小端在 `+0x9C + 10`。
- 拿到根目录 LBA 后，`seek` 到 `root_lba × 2048` 读 `root_size` 字节，就得到根目录的目录记录序列，
  然后可以逐条解析、递归进入子目录。

### 3.2 目录记录（directory record）

每个文件/子目录对应一条目录记录。常用字段偏移（相对记录起点）：

| 偏移 | 含义 |
|---|---|
| `+0` | 本记录长度（字节）；读取时用它跳到下一条 |
| `+2` | extent（起始 LBA），**小端（LE）** |
| `+6` | extent，**大端（BE）**——同一值的另一字节序副本 |
| `+10` | 文件大小（字节），**小端（LE）** |
| `+14` | 文件大小，**大端（BE）** |
| `+25` | 文件标志位（`flags & 2` 表示这是一个目录） |
| `+32` | 文件名长度；`+33` 起是文件名字节 |

目录里还有两条特殊项 `.` 与 `..`：它们以「名字长度 = 1、名字字节 = `0x00` / `0x01`」的形式
存在，解析目录树时需跳过，不要把它们的字段当成普通文件记录。

### 3.3 双端序（both-endian）

**关键语义**：extent 和 size 都是**双端序**存储——同一字段在记录里写两遍（LE + BE）。
改落点或改长度时，**两端必须同时改且值一致**，否则模拟器/游戏按旧值去读，
就会读到旧数据或错位数据。改完应校验「所有受影响记录的 LE == BE」。

## 装配流程

### 4.1 三种落点形态对照

| 形态 | 适用条件 | 是否改 ISO9660 | 典型场景 |
|---|---|---|---|
| 原位写回 | 新文件长度与原文件**完全相等** | 不改 | 等长文本替换、等长补丁 |
| 末尾追加 | 新文件**变长** | 改 extent + size（双端序） | 更大的字库、变长译文容器 |
| 容器内追加 | 新数据放容器内部空闲区/尾部 | 不改（容器大小不变时） | 把新子文件塞进主容器的孤儿区 |

### 4.2 原位写回

新文件长度与旧文件完全相等时，直接 `seek` 到 `LBA × 2048` 覆盖写入即可，无需改 ISO9660。
前提是**内容内部结构没有破坏**：字符串池、指针、目录条目等都要保持原布局（等长替换的规则见
「04-回写与压缩.md」）。写完后做回读比对确认无截断。

实例：某菜单文件（游戏内结构名 `OLMENU.BIN`，1165568 字节）做等长替换时，直接原位写回其
原 LBA（`0x0506`），不改目录记录。

### 4.3 末尾追加

新文件变长时，把新文件写到**原镜像总扇区数之后**（即 ISO 文件末尾），这是最安全的
「不覆盖任何原数据」的落点。之后更新目录记录：

- extent：`+2` 写 LE、`+6` 写 BE（新 LBA）；
- size：`+10` 写 LE、`+14` 写 BE（新字节长度）。

实例：约 660 MB（660333653 字节）的新主容器变长后，追加到原镜像总扇区数之后（LBA `1454736`），
再把 `AC.BIN;1` 目录记录的 extent/size 按上述双端序更新；追加后校验该 LBA 处头为 `BND\0`，
并确认各视频头 `00 00 01 BA` 未受影响。

PVD 里还有一个「卷空间大小」字段。本项目经验是：**该字段保持原值即可**，模拟器/游戏按目录
记录读取，不依赖它（实测可玩已验证）；如你的目标平台另有要求，请自行实测。

### 4.4 容器内部追加（BND 槽更新）

ACLR 的主数据文件（游戏内结构名 `AC.BIN`）本身是 BND 容器：头部之后是一张**目录槽表**，
每条槽描述一个子文件。实测结构：

- 容器头：`+0x0C` 是容器总大小，`+0x10` 是子文件数量；
- 槽表从 `+0x20` 起，**每条 16 字节**：`eid`（4）+ `offset`（4，在 `+4`）+ `size`（4，在 `+8`）
  + `flags`（4，在 `+12`）。

往容器内部追加子文件时：

1. 新子文件写到容器内某块空闲区/尾部，**offset 必须 0x800（2048）对齐**——游戏按扇区读，这是硬要求；
2. 更新该子文件槽的 `offset`（`+4`）与 `size`（`+8`）；
3. 若容器整体变长，更新容器头 `+0x0C` 的总大小（进而可能要改 ISO9660 里该容器的 size）。

### 4.5 从 PVD 定位到目标目录记录的完整步骤

1. `seek(16 × 2048)` 读 PVD，校验 `CD001` 魔数；
2. 从 PVD `+0x9C` 读根目录记录，取根目录 LBA（小端）与大小；
3. `seek(root_lba × 2048)` 读根目录，逐条解析目录记录（按 `+0` 的记录长度前进）；
4. 遇到子目录（`flags & 2`）递归进入，直到找到目标文件名的记录；
5. 记录下「目标记录在镜像里的绝对偏移」以及它的 extent/size，用于后续 patch；
6. 写入数据后，回到该记录偏移，按双端序更新 extent/size。

### 4.6 完整装配步骤（原位 patch 路线）

1. 读出原镜像的 PVD，拿到根目录 LBA/size；
2. 遍历目录树，收集目标文件的目录记录偏移、extent、size；
3. 决定落点：等长 → 原位写回；变长 → 末尾追加；
4. 写入数据（容器内部追加时同步更新 BND 槽 + 头部大小）；
5. 更新 ISO9660 目录记录的 extent/size（双端序）；
6. 校验（见下一节），校验不通过即停止。

## 落点验证方法论

**红线：禁止靠「看起来全零」判断空闲区。** 全零字节完全可能出现在某个文件**内部**
（例如视频流内部的填充），它并不是「没人用的空间」。

### 5.1 一个真实的翻车案例

- 装配时想给新主容器找「首个空闲扇区」，找到 LBA `915676`，注释里写「某大文件之后的首个空闲扇区」；
- 实际上，视频目录从 LBA `915631`（ES1.PSS）就开始了，`915676` 只是 **ES1.PSS 内部的
  一段全零区**，被误当成空闲；
- 结果：660 MB 的新主容器从 `915676` 写起，完整覆盖了 `915631 ~ 1264644` 这段视频区
  （ES1~ES5 及 ES6 前半段）；
- 而开场视频 I1.PSS 起点是 `1264645`，在覆盖区**之后**——所以「开局有视频、结局必黑屏」，
  且自由任务不播结局 CG，很难复现。

这个案例说明：**「看起来全零」不等于「空闲」**，只有「文件表区间不相交」才算数。

### 5.2 正确的验证三件套

1. **区间不相交断言**：以权威文件表为输入，把每个文件的区间 `[LBA, LBA + ceil(size/2048))`
   求出来，然后断言「新文件落点区间」与「所有原文件区间」**两两不相交**。这一步应该
   写成自动检查，每次装配都跑。
2. **魔数抽检**：写入后对关键位置读头几个字节核对——
   - BND 容器头：`BND\0`（`42 4E 44 00`）；
   - PSS 视频头：`00 00 01 BA`（MPEG-PS pack 起始码）。
3. **回读比对**：把写进去的整段读回来，与原字节逐字节比较，确认无截断、无错位。

## 高位偏移限制

游戏对**容器内部子文件 offset** 有高位上限，追加文件不能无限往后堆。

ACLR 实测：字库在 **626.4 MiB** 处能读、部件在 **583.5 MiB** 处能读，而**任务容器在
628.8 MiB 以上读不了**；任务装载器的 offset 上限大致在 **626~628 MiB** 之间。
超过上限的表现是任务卡在加载界面。修复方法是把高位容器整体搬到低位空闲区（约 519 MiB 起），
使全部任务 offset 落在上限以内（修复后全部任务 offset ≤ 524 MiB）。

排查这类「位置相关」的加载失败，有一个高效对照：**把「原版数据」放到「追加位置」**。
如果原版内容放在新位置也失败，说明是**位置**问题，不是**内容**问题——一轮就能定方向。
（反例佐证：同一份数据，放在低位能进、放到 ~629 MiB 就卡，内容没变，唯一变量是位置。）

## 孤儿区 ≠ 空白区

原版容器结束（约 544 MiB）到追加区起点之间，可能有一段看似空闲的区域。ACLR 实测这段约
63 MiB 的区间**不是真空闲，而是 94% 以上非零的「孤儿死数据」**：早期装配流程追加过、
后来又被覆盖/回退的旧容器残留，数量可达数百个。

- 它们**没有任何 BND 条目引用**——游戏只通过 BND 目录读子文件，所以理论上可安全覆盖；
- 但**绝不能当成「空白区」随意占用**：覆盖前必须确认「目标区间不与任何被引用条目重叠」，
  并且不要假设其内容是零、也不要假设零就是安全。

一句话：**孤儿区是「可回收的覆盖目标」，不是「空白区」。**

## 瘦身与前移

### 8.1 什么时候需要瘦身

末尾追加会让镜像比原版大。ACLR 的汉化镜像体积构成（实测）：

- 原版镜像约 `2,979,299,328` 字节；
- 末尾追加汉化主容器约 `660,333,653` 字节 → 合计约 `3,639,632,981` 字节；
- 但 LBA `3197` 处的旧主容器（约 `544,447,952` 字节）已被目录弃引用（`AC.BIN;1` 指向末尾新容器），
  成为**死数据**，白白占着 544 MB 可回收空间。

### 8.2 前移的基本动作

删除一段死数据后，它后面的所有文件要**整体前移**，并同步更新目录记录。ACLR 实际前移案例：

- 死数据起点 LBA `3197`，其后的 BMSS 等文件起点 LBA `269041`，前移量
  `= 269041 - 3197 = 265844` 扇区（`= 544448512` 字节，向上取整对齐）；
- 受影响文件约 **37 个**（BMSS + 结局视频 ES1~ES6 + 开场视频 I1 + 键位演示 + 邮件演示 +
  结尾视频 + 新主容器），全部更新双端序 extent；
- 前移后镜像从约 3.39 GiB 缩到 **2.88 GiB**，省约 **519 MiB**；
- 校验：逐文件 MD5 对比「前移前后」全部一致（移位无损）、各视频头 `00 00 01 BA`、
  新主容器新 LBA 处头 `BND\0`、37 个文件 extent 的 LE==BE。

### 8.3 两条必须遵守的纪律

1. **正向拷贝**：前移（目标 < 源）必须**从低地址向高地址**拷贝。反向拷贝会先把「尚未读出的
   源数据」覆盖掉，导致数据损坏——本项目第一次跑反了，视频头校验直接失败。
2. **先验证再前移**：游戏可能**硬编码某些文件的 LBA 引用**（历史上装配脚本就曾硬编码主容器
   LBA，导致覆盖了视频区）。前移会让所有后续文件 LBA 改变，若游戏按硬编码 LBA 读，前移后
   会黑屏/卡死。**必须先动态验证游戏读这些文件用的是目录 LBA 还是硬编码值，未验证前不要动。**

### 8.4 视频缩身（PSS 变长截断）

PSS 视频也可以按内容真实长度截断以回收空间：把视频内容截到最后一个内容 pack 的结束，
并在末尾紧跟 MPEG-PS 结束码 `00 00 01 B9`（B9 紧跟内容，解复用器读到即结束）。截断后
其后的文件整体前移相应扇区数，更新受影响文件的 extent LBA、更新该视频的 size。
（PSS 结构的细节见「06-PSS视频.md」。）

## 装配前检查清单

动手之前逐项确认：

- [ ] 有权威文件表（每个文件的 LBA + size），并已用于区间计算；
- [ ] 新文件落点区间与文件表**所有区间不相交**（或明确落在「无条目引用的孤儿区」）；
- [ ] 变长文件放在 ISO 末尾（原总扇区数之后），不覆盖任何原数据；
- [ ] ISO9660 目录记录 extent/size 的 **LE 与 BE 都已更新且相等**；
- [ ] 容器内部追加的子文件 **offset 已 0x800 对齐**，且低于游戏高位上限
  （ACLR 任务装载器约 626~628 MiB）；
- [ ] 容器头总大小（`+0x0C`）、子文件槽 offset/size 已同步更新；
- [ ] 前移（若做）：**正向拷贝**、尾部截断、所有受影响 extent 更新；
- [ ] 魔数抽检通过（BND 头 `BND\0`、PSS 头 `00 00 01 BA`）；
- [ ] 回读写入段与原数据逐字节一致；
- [ ] 若改动了视频/主容器落点，实测开场、结局、任务、机库、存档读档等关键路径。

### 9.1 装配后必做的四步快速自检

1. 目标文件在**新 LBA 处**的头几个字节正确（BND 容器 = `BND\0`、PSS = `00 00 01 BA`）；
2. 目录记录里该文件的 **extent LE == BE**、**size LE == BE**；
3. 写回段回读后与原数据**逐字节一致**；
4. 用文件表重新算一遍，**新落点区间与所有文件区间不相交**。

这四步全绿，才进入模拟器实测环节。

## 坑与教训

| 现象 | 根因 | 规避 |
|---|---|---|
| 主线结局任务打完 Boss、结算前**必黑屏**；自由任务却复现不了 | 新主容器落点被误判为「首个全零空闲扇区」，实际是结局视频 ES1.PSS 内部的一段全零，结果完整覆盖了结局视频 ES1~ES6；开场视频 I1 在覆盖区**之后**所以开场正常、结局才黑屏 | 落点必须是 ISO 末尾或经文件表验证的空闲区；装配后自动断言新区间与所有文件区间不相交 |
| 个别任务卡在加载界面进不去 | 任务容器被追加到 ~628 MiB 以上，任务装载器读不了高位 offset（上限约 626~628 MiB） | 追加子文件控制 offset 低于上限；空闲落点优先选「原版数据结束后的孤儿区」；用「原版数据放到追加位置」二分对照分离内容与位置 |
| 前移后视频头校验失败 | 前移（目标 < 源）却从高到低反向拷贝，覆盖了尚未读出的源数据 | 前移一律**正向拷贝**（低 → 高） |
| 某段区间看起来「空闲」就直接占用 | 63 MiB 区间 94%+ 非零，是早期装配追加后被覆盖/回退的旧容器残留（孤儿区），只是无 BND 条目引用 | 孤儿区可回收但必须先确认无条目引用；不能按「空白区」随意占用 |
| 瘦身/前移后黑屏或卡死（若发生） | 游戏可能硬编码了某些文件的 LBA 引用，前移改变了这些文件的 LBA | 前移前先动态验证游戏读这些文件的 LBA 来源（目录 vs 硬编码），未验证不轻易动 |
| 改完落点模拟器仍读旧数据 | ISO9660 extent/size 双端序只改了一端，或两端值不一致 | 改后校验 LE==BE，且回读验证 |
