# 03 · 字库与渲染

> 本篇回答一个问题：PS2 游戏里的汉字是怎么「画」出来的，以及如何在不改游戏渲染代码的前提下，把自备字体渲染出的简体字形塞进游戏原有的字库，让它们沿着游戏既有的解码、上传、采样链路正常显示。

## 背景与目标

ACLR（ARMORED CORE LAST RAVEN）的文本渲染不是操作系统级的 TrueType 渲染，而是游戏内置的几套**位图字库**：每个字符预先光栅化成一张小位图，运行时按字符编码查表、取位图、上传显存、采样绘制。汉化要做的不是「换字体引擎」，而是：

1. 逆向每套字库的**文件结构**（头、区间表、字形表、位图区、调色板）。
2. 用自备字体把需要的简体字形渲染成游戏期望的**位图格式**（4bpp 索引像素 + 特定排布）。
3. 把新字形**追加或覆盖**进字库，同时遵守游戏的对齐、大小、偏移等硬约束。

目标产出：一套覆盖简体用字、在实机上字形清晰且与其余界面观感统一的字库。

## 前置依赖

- 正版游戏镜像（自备），以及按《01-解包.md》提取出的字库容器（`AC.BIN` 内的 `font.bnd` 与顶层归档中的 `0A93`）。
- Python 3 + Pillow：Pillow 的 FreeType 后端负责把 TTF/OTF 光栅化为灰度图。
- 一款自备的中文黑体/无衬线字体（例如开源 Noto 系列；本教程不提供、也不推荐任何具体字体文件）。
- 基本概念：PS2 GS 的 **4bpp 索引纹理（PSMT4）** 与 **CLUT（调色板）**——像素存的是 0–15 的索引，真实颜色由 CLUT 查表得到。
- 编码背景见《02-文本与编码.md》：SJIS、MAPPING 码（自造高位码点）、UTF-16LE。

## 一、字库体系总览

游戏里主要有三套字库，编码与位图格式各不相同，不能混用：

| 字库 | 用途 | 编码方式 | 位图格 | 关键特征 |
|---|---|---|---|---|
| `ac0_j1` | 机库 / 菜单 / 系统消息 / 名单 / 任务列表 | SJIS → 字形槽 | 每行 512B = 32×32 PSMT4 | **变宽**（8px/16px）、**交错布局**、`tail×512` 寻址 |
| `0A93` | 局内对话 | Unicode 区间 → 字形槽 | 每字 128B = 16×16 4bpp | **固定宽**、线性布局、**16 字节对齐** |
| `ID=9`（内部叫 `ac0_j6`） | TUNE 参数标签 / 属性页标签 | MAPPING 码 + 自然 SJIS | 每字 128B = 16×16 4bpp | 小字库；追加要 **pad 对齐** 且 **size 同步三处** |

其中 `ac0_j1` 与 `ID=9` 都是 `font.bnd` 内的子文件（`ac0_j1` 是第 0 号子文件，`ID=9` 是第 9 号子文件）；`0A93` 是顶层归档中一个独立的字库容器。

## 二、通用结构骨架：头、区间表、字形表

这几套字库共享同一套「`.fnt` 式」骨架，只是字段语义略有差异。以 `ac0_j1` 为例：

```
0x00  ver   = 0x0101
0x04  size  = 整库字节数
0x0E  行数  = 位图行数（每行 512B）
0x10  页数  = 1（只有一张纹理页）
0x12  flags = 0x02（bit0=0 → 变宽/比例字体）
0x40  区间表（每条 8B）
0x250 字形表（每条 24B）
0x14280 字形格描述字 = 0x55408000（PSMT4 尺寸/格式）
0x142D0 位图区（每行 512B）
```

`0A93` 的头字段与之类似，但偏移通过指针字段给出：

```
0x0A  区间数 n
0x0C/0x0E  字形数 g
0x10  页数 = 1
0x12  flags = 0x03（固定宽）
0x20  区间表指针 = 0x40
0x24  字形表指针
0x28  texdesc（112B，纹理描述符）
0x30  位图指针
0x34  pitch = 128（每字形字节数）
```

两条通用条目格式：

- **区间条目（8B）**：`[起点 u16][终点 u16][起始字形槽 u16][保留 u16]`。作用是把一段连续的码点映射到一段连续的字形槽。
- **字形条目（24B）**：`[u0,v0,u1,v1 四个 float（UV）][宽 u16][高 u16][tail u16]`。`tail` 是定位位图的关键字段。

解码链（以 `ac0_j1` 为例）：

```
字符码 → 二分查找区间表 → 字形槽 g → 字形条目里的 tail → 行号
      → 位图基址 + tail×512 → 上传 VRAM → 按 UV 采样绘制
```

## 三、三套字库的结构细节

### 3.1 `ac0_j1`：变宽字体（不是固定 16×16）

这是最容易误判的一套。`ac0_j1` 的 `+0x12 = 0x02`，是**比例/变宽字体**：一行 512B（32×32 纹理）按 8px 网格排布**数量不定的字形**，而不是固定每行 4 个 16×16。

实测 UV 档位：

- U 档位：`0 / 0.25 / 0.5 / 0.75 / 1.0`（4 列，8px 网格）
- V 档位：`0 / 0.5 / 1.0`（2 行，16px）
- 宽度分布（845 字形样本）：**770 个 16px 宽 + 75 个 8px 宽**，高度统一 16px

每行字形数也不固定：实测有 1 个、2 个、3 个、4 个，甚至 6/7/8 个的行。例如 `tail=0` 那行是「1 个 16px 字（占 2 列）+ 6 个 8px 字」，共 7 个字形。

**结论**：对 `ac0_j1`，不能假设「每行 4 个 16×16 四象限」。UV 四象限值虽然碰巧与 16px 字形一致，但位图的排布规则完全不同。

### 3.2 `0A93`：固定宽 16×16，Unicode 区间

`0A93` 是固定宽字库：每个字形 16×16 @4bpp = 128B，`bitmap + tail×128` 定位，UV 恒为 `(0,0,1,1)`。它直接用 Unicode 区间表映射（对话文本以 UTF-16LE 回写），原版有 671 个区间 / 877 个字形。

**字形数上限不是 877**：上传是「惰性单槽」——渲染时只把当前那个 16×16 字形上传到固定 VRAM 槽，与纹理总高度无关。实测扩展后 1000+ 字形（如 1161 字形）仍正常，前提是对齐正确（见第八节）。

### 3.3 `ID=9`：TUNE 标签小字库

`font.bnd` 的第 9 号子文件，专管 TUNE 参数标签与属性页标签。要点：

- 头 `+0x08 = 0x10`（字形宽 16）是**固定字段，重建时必须原样保留**。
- 区间表 8B/条；字形表 24B/条（`tail` 在 `+22`）。
- 位图线性 4bpp，`bitmap + tail×128` 定位；**`tail` 是位图行号，不是字形序号**（原版小字库里 tail 本身是乱序的）。
- CLUT 在页表 `+0x30`，16 项 × 4B，**乱序** nibble→alpha。
- 布局顺序：`头 0x40 + 区间表 + 字形表 + 页表 0x10 + texdesc 0x20 + CLUT 0x40 + 位图(128B×n)`；**页表之后必须 16 字节对齐**。

## 四、位图：交错布局 vs 线性布局

**这是「字形串位/分裂」类 bug 的核心**，两条布局规则不能混。

### 4.1 线性布局（`0A93`、`ID=9`）

4bpp 每字节装 2 个像素，**低半字节 = 左像素**（偶数列），高半字节 = 右像素。写像素的伪代码：

```python
def set_px(block, x, y, v):
    # 16x16, 每行 8 字节
    bi = y * 8 + x // 2
    if x % 2 == 0:
        block[bi] = (block[bi] & 0xF0) | v        # 左像素 → 低半字节
    else:
        block[bi] = (block[bi] & 0x0F) | (v << 4) # 右像素 → 高半字节
```

注意：把高低位写反，字形会**镜像或破碎**，这是常见坑。

### 4.2 交错布局（`ac0_j1`）

`ac0_j1` 每行 512B = 32×32 PSMT4，是**交错（interleaved）**排布：

```
每行 16 字节 = [左 16px 8B][右 16px 8B]
上半 16 行 = [col0|col1]      下半 16 行 = [col2|col3]
字节序 = col0r0 col1r0 col0r1 col1r1 ... col0r15 col1r15
         col2r0 col3r0 col2r1 col3r1 ... col2r15 col3r15
```

即「左右两列逐行交替」而不是「col0 连续 128B、col1 连续 128B」的线性写法。字节级寻址公式（4bpp PSMT4 交错）：

```
block_offset = 0x142D0 + tail*512 + half*256 + i*16 + col*8
half = 0 if col < 2 else 1     # 上半 / 下半
col  = round(u0/0.5) + round(v0/0.5)*2   # 由字形表 UV 反推
i    = 0..15                    # 行内 16 行，每行 8 字节
```

把线性布局的字形写进交错字库，采样时就会把相邻字形的字节交叉读进来，表现为**字形上下两半串位、垂直压扁**。

## 五、CLUT 调色板与「乱序」

4bpp 像素存的是 0–15 的索引，最终颜色 = `RGBA(128,128,128, ALPHA[v])`，`ALPHA` 是字库自带的 16 项表。例如 `0A93` 的 alpha 表：

```
ALPHA = [0,0,51,59,16,128,85,59,24,111,103,93,119,8,69,34]
```

**最大的坑是 CLUT 并非「索引越大越亮」的线性渐变，而是乱序的。** 在一套 32×32 入场名字库上，用 PCSX2 纹理转储逐像素反推，得到的真实 nibble→(亮度, alpha) 映射为：

```
0:(0,0)   1:(255,128)  2:(224,96)  3:(32,0)   4:(64,32)
5:(192,96) 6:(160,64)  7:(128,64)  8:(96,32)  9:(32,32)
10:(160,96) 11:(96,64)
```

关键事实：

- 白核 `nib1` 的 alpha 是 **128（半透明）**，不是 255。
- `nib3` 的 alpha 是 **0（完全透明）**。
- `nib2~11` 的亮度**乱序**：`2 > 5 > 10 > 6 > 7 > 11 > 8 > 4 > 9 > 3`。

后果：如果用「脑补的 16 级平滑 ramp」做预览，预览看着正常，实机会发灰、发毛刺。正确做法是：**用游戏纹理转储反推真实 CLUT，再按 CLUT 的 RGB 亮度做最近匹配量化**（低于阈值判透明）。灰度→nibble 的量化伪代码：

```python
def quantize(gray):
    a = gray                          # 0..1
    target = round(min(1.0, a ** gamma) * 128)  # gamma 控制笔画粗细
    nib = nearest(target, CLUT_BRIGHTNESS)       # 按亮度最近，不是按序号
    return nib
```

## 六、渲染链路与采样

两套主要字库的采样参数不同，机器码级确认：

- **`ac0_j1`**：从字形格描述字 `0x55408000` 解出 **U_scale=32、V_scale=2**；采样坐标 `U = 2.0 + u0*32`、`V = 2.0 + v0*2`（`+2.0` 是 padding）。U 方向 4 个 8px 列、V 方向 2 行，正是变宽字体的特征。（旧结论「U=V=32」是误算。）
- **`0A93`**：**U_scale=V_scale=16**，UV 恒为 `(0,0,1,1)`，采样整格 16×16（offset `+2.0`），运行时不被覆写；上传是惰性单槽（字形上到 VRAM `0x3A60`，CLUT 8×2 上到 `0x3FC0`）。

`ac0_j1` 的 tail→位图函数带边界检查（`tail < 行数`），返回 `位图基址 + tail×512`；渲染器再按字形表 UV 定位行内的 col/half。

## 七、替换流程（伪代码）

把「自备字体 → 字库字形」的完整流程梳理如下：

```python
# 1. 收集字符集：译文实际用字 + 全 ASCII + 需要的全角/符号
chars = collect_chars()

# 2. 逐字渲染：32px em 全角框光栅化 → 灰度（不裁墨迹）
#    可选：2×2 盒式平均缩小到目标格；需要加粗时用「多亚像素偏移取 max」而非描边
for ch in chars:
    gray = render_32px(ch)            # FreeType 渲染
    gray = box_downsample_2x2(gray)   # 2:1 盒式平均，避免 LANCZOS 振铃
    # 3. 对比度曲线：gray = gray ** gamma（gamma 略大于 1 可收紧笔画）
    # 4. 量化：灰度 → 按真实 CLUT 亮度最近匹配 → nibble
    block = pack_4bpp(gray, layout)   # layout = 'linear' 或 'interleaved'
    glyphs.append(block)

# 5. 重建区间表（按码点排序、合并连续区间）+ 字形表（UV/tail/宽高）
# 6. 计算位图偏移，必要时在字形表后补 pad 到 16 字节对齐
# 7. 同步所有 size 字段（头、目录条目、路径表条目）
# 8. 就地覆盖/追加，保持所在容器与整张镜像的总大小不变
```

其中「无阴影」「不描边」是观感统一的关键：描边加粗在低分辨率下容易把笔画缝隙填死（粘连），小字号尤其明显。

## 八、16 字节对齐：未对齐 → 全体字形融化

`0A93` 的 texdesc / CLUT / 位图由游戏用 **DMA 上传**，必须 **16 字节对齐**。未对齐时，数据本身全对，但上传后**全体字形错乱、融化**。

关键公式（`0A93`）：

```
位图偏移 = 0x40 + n*8 + g*24 + 112
mod16    = 8*(n + g) mod 16
```

因为 `8*(n+g) mod 16` 只由 `n+g` 的奇偶决定，所以：

> **只有当「区间数 n」与「字形数 g」同奇偶时，位图才 16 对齐。**

原版 671 区间 / 877 字形（都是奇数）→ 对齐；而「822 区间 / 877 字形」（奇偶不同）→ 未对齐 → 坏。修复方法：在字形表之后插入 `pad = (-texdesc_off) % 16` 字节（只会是 0 或 8 字节），并同步修正 texdesc 的相对指针。数据锚点：

- 原版：671 段 / 877 字形，位图 `@0x67E0`（16 对齐）。
- 修复后：822 段 / 877 字形，位图 `@0x6CA0`（补 8 字节 pad 后对齐）。

**教训**：改二进制格式时，「数据正确 ≠ 能跑」。字对、字形对、区间对、CLUT 对，唯独漏了字节对齐，也会全坏。排查「数据全对却坏」时，优先查**对齐 / 边界 / 奇偶性**。

## 九、追加字形：pad 对齐、size 同步与零扩容

### 9.1 pad 对齐

追加字形（区间数或字形数变化）会让位图偏移漂移，重建工具应在字形表后统一做 `(-off) % 16` 的 pad（第八节）。`ID=9` 同理，页表之后必须保持 16 字节对齐。

### 9.2 size 同步三处（`ID=9` 追加时的教训）

改了子文件大小后，不能只改一处，否则要么不生效、要么崩溃。需要同步：

1. `font.bnd` 头部 `+0x0C` 的 size；
2. `font.bnd` 目录表中该子文件的条目 size；
3. 外层归档路径表里指向该子文件的条目（同一子文件可能登记多份，例如 7 个路径表条目 `0x031A–0x0326`）。

### 9.3 零扩容约束

三套字库都嵌在更大的归档里，**整体大小不可变**：

- `ac0_j1` 所在的 `font.bnd` 后面没有空闲 gap，扩容必须整体搬迁，禁止原地加行；
- `ID=9` 只能**就地覆盖** `font.bnd` 之后的死数据区，**不能插入字节**——插入会平移后续数据，直接导致 VIF FIFO 崩溃；
- 补字形因此只能用「**覆盖未被游戏文本引用的原日文字形槽**」，而不是新增行。

**空闲槽判定必须扫全语料**：译文语料、菜单/UI 文本、名单、报告等一个都不能漏。典型事故：误把希腊字母码位当空闲槽。游戏菜单/UI 与对话说话人（如 `Ω：`）实际在用希腊字母区 `0x839F–0x83B6`（Α–Ω），例如 `0x839F=Α`、`0x83A0=Β`、`0x83B5=Ψ`——把简体字形注入这些槽，会导致界面该显示希腊字母的地方全部错乱。判「空闲」的唯一标准：该码位在**全部语料**中出现次数为 0。

## 十、坑与教训

每条按「现象 → 根因 → 规避」组织。

1. **字形上下两半串位/压扁** → 交错字库被写成了线性排布 → 写位图前先确认目标字库是 `interleaved` 还是 `linear`，按对应对齐公式逐字节写。
2. **错位却查不出数据错误** → 把变宽字体当固定 16×16 四象限 → 排查渲染错位前，先统计字形表 UV 档位，确认「等宽 vs 变宽」。
3. **数据全对但全体字形融化** → texdesc/CLUT/位图未 16 字节对齐（n 与 g 奇偶不同）→ 重建后强制 `(-off) % 16` pad，再修正相对指针。
4. **预览正常、实机发灰/毛刺** → 用脑补的线性 ramp 量化，实机 CLUT 是乱序的 → 用纹理转储反推真实 nibble→(亮度,α)，按亮度最近匹配量化。
5. **字形镜像/破碎** → 4bpp 字节内偶列高低位写反 → 记住「偶列=低半字节、奇列=高半字节」。
6. **错字/串位** → 用「glyph 序号 × 128/512」算位图，忽略了 `tail` 才是位图行号 → 位图寻址一律走 `tail` 字段（`tail×512` 或 `tail×128`），别用字形序号。
7. **追加后崩溃或不生效** → size 只改了头没改目录/路径表 → 列清单，把所有引用该子文件 size 的位置一次同步。
8. **补的字覆盖了游戏在用字形** → 空闲槽只扫了译文语料 → 判空闲前扫全语料（含菜单/UI 文本、希腊字母区），确认该码位 0 出现。
9. **插入字节导致 VIF FIFO 崩溃/后续数据错位** → 在归档中间插入 → 只就地覆盖，不插入；零扩容。
10. **字高低不平** → 按「质心居中」逐字重渲，每个字重心漂移 → 统一用顶对齐/基线对齐（画布固定 y 画字，按 ascent 顶对齐），底部对齐 row 基线。
11. **笔画两端粗细不均/发糊** → 渲染用了小数坐标产生半像素错位，或超采样+缩小+level 把 AA 压成近白/近黑跳变（banding）→ 用整数坐标光栅化；尽量复刻原字库的栅格化尺寸与滤波，或直接用真实 CLUT 量化。
12. **复杂笔画字低分辨率断笔/横滑** → 16px 直渲的 hinting 对某些字把笔画渲得过细 → 可尝试高分辨率渲染再缩小（注意缩小滤波别引入振铃），最终以实机目检为准；个别顽固字形需单独重渲。

> 通用心法：渲染错位先查「数据布局」而不是「数据内容」；关键数字（缩放、tail、对齐、CLUT 顺序）要回字节或机器码复核，不要引用二手结论。
