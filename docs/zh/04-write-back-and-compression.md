# 04 · 回写与压缩

## 背景与目标

本篇解决一个问题：把已经翻译好的文本安全地"塞回"游戏容器。回写不是简单地改几个字节，而是要同时满足三层约束：

- **压缩层**：修改后的数据要能通过游戏自己的解压器（fsliblzs / LZSS）。
- **长度层**：替换不能改变字符串的相对位置（等长），否则偏移引用会断裂。
- **结构层**：字符串池的分隔符、块标记、标识符等"隐性结构"必须原样保留。

只关注"译文对不对"，通常只会得到"图标在、文字空白"或"进机库卡死"这类诡异结果。本篇按"压缩兼容性 → 等长/变长 → 结构保真 → 回写清单"的顺序展开，末尾汇总坑与教训。

## 前置依赖

- 已完成解包（BND 嵌套、fsliblzs 解压，见 [01 · 解包](01-unpacking.md)）与文本/编码分析（SJIS、MAPPING 码、容器 id，见 [02 · 文本与编码](02-text-and-encoding.md)）。
- 译文用到的每个汉字都已在字库里有对应字形（见 [03 · 字库与渲染](03-fonts-and-rendering.md)）；回写只负责把"能显示的文本"放进正确位置。
- 建议准备 Python 3（标准库即可）与一个能按字节比对 / 十六进制查看的工具，用于回写后的校验。

## 一、fslzss / fsliblzs 压缩兼容性

### 1.1 格式速览

游戏里大量容器是 `fsliblzs` 压缩文件（本作中这类容器共 2469 个）。头部 0x2C 字节：

| 偏移 | 字段 | 端序 / 取值 |
|---|---|---|
| 0x00 | 魔数 `fsliblzs`（8 字节） | ASCII |
| 0x10 | 文件总大小（含 0x2C 头） | u32 LE |
| 0x14 | 压缩标志 | u32 = 1 |
| 0x20 | 窗口 / 块大小提示 | 原版恒为 0x00000100(256)，游戏解压器不读 |
| 0x24 | 解压后大小 | u32 BE |
| 0x2B | raw 标志 | 0 = 压缩 / 1 = 原样存储(raw) |
| 0x2C | LZSS 流起点 | — |

LZSS 流是"8 操作一组、每组 1 个 flag 字节、位序 LSB 优先"的经典布局：

- flag 位 = 0：字面字节，直接透传 1 字节。
- flag 位 = 1：回引项 2 字节 `[b1, b2]`：
  - `dist = (b1 << 4) | (b2 >> 4)`（12 位）
  - `len = (b2 & 0xF) + 1`（1..16）
  - `src = max(0, 当前输出长度 - 0x1000) + dist`
- 结束标记：回引项 `00 00`（length nibble == 0）。

游戏侧解压器的完整逆向结论（函数位置、窗口语义、结束判定等）见 [01 · 解包](01-unpacking.md)。

### 1.2 往返无损 ≠ 游戏兼容

写压缩器时最容易犯的错，是用"自己的解压器能否解回"当作验收标准。这只证明压缩器与解压器**自洽**，不证明游戏能解，更不证明其它数据路径没坏。

项目实测踩过一次：把部件数据解压、改描述、再用自写压缩器重压后，机库 3D 预览里若干部件贴图损坏（进任务 / 测试场后同一部件又正常）。二分定位后得到的规律是：

| 数据 | 内容 | 处理策略 |
|---|---|---|
| 5xxxx（如 51309） | 参数 + 3D 模型 + 贴图 + 名称 + 描述（约 99 KB） | **保持原版压缩，绝不第三方重压** |
| 6xxxx（如 61309） | 参数 + 名称 + 描述文字（约 16 KB） | 可解压 → 改描述 → 重压 |
| 对话 `.mes` | 纯文本 | 可重压 |

关键事实：**机库显示的部件描述文字其实由 6xxxx 提供**（16 KB 小文本，重压后游戏能正常解）；5xxxx 里的描述从没被机库显示过。因此翻译部件描述只需动 6xxxx。

另外注意：raw（0x2B=1）标志对部件加载器无效——它仍按压缩流去解，结果是 3D 预览空白。raw 只对少数文件类型有效（原版里唯一的 raw 文件是 0xFA00）。

### 1.3 更精确的结论（引 01）

后续逆向游戏解压器后，上述"二进制坏、文本好"的归因被进一步修正：游戏只有一个 fsliblzs 解压器，其行为与参考解压实现**逐字节一致**（窗口 0x1000、dist 相对窗口起点、length=nibble+1、结束只看 nibble==0），并且**完全不读头部 0x20 字段**；实测重压后的 18.8 万字节模型数据在游戏算法下也能逐字节还原。

这意味着 LZSS 算法本身不是元凶，真正的坏因更可能出在**解压之前的装载 / 目录层**（BND 目录 offset/size 回写）。所以 1.2 的操作规则（别重压 5xxxx）仍然是安全底线，但排查这类 bug 时应优先检查"目录 / size 同步"，而不是急着怀疑压缩算法本身。详细结论见 [01 · 解包](01-unpacking.md)。

## 二、等长替换与变长替换

### 2.1 规则

- **等长替换：安全，可以直接做。** 例：`総(0x918D)→综(0x89C5)`、`対(0x91CE)→对(0x88BB)`，都是 2 字节→2 字节，不移位。
- **变长替换：默认禁止。** 字符串常被偏移 / 索引引用，变长会移位后续所有字符串，使引用全部失效。

### 2.2 为什么变长会炸

以 MRB 的 STR 段为例：字符串从 0x20 起，size/count 记在头部 0x14/0x18，段外有 2146 个 u32 值落在 0x20~0xEA0 范围内，即大量字符串被外部偏移引用。任何一处变长（哪怕 ±2 字节）都会移位后续字符串 → 引用断裂 → 进机库卡死。

常见的变长替换包括：

- 增减字数：`移動力→移动性能`（+2 字节）
- 全角↔半角：`ＥＮ→EN`（−2 字节）

**全角→半角在直觉上"缩短了"，但它同样是变长，同样禁止。** 要变长替换，必须先逆向清楚引用结构（是字符串索引还是字节偏移）、并同步更新所有引用，否则一律按禁止处理。

## 三、结构保真：不止长度

"等长替换"只保证文件总长不变，**不保证池内部结构不变**。分隔符、块标记、NUL 段分布都属于必须单独保真的结构。

### 3.1 典型事故：0x00 填充破坏字符串池

按键说明栏（key guide）的字符串池，原版 NUL 段结构严格是 **{单 NUL, 双 NUL}**：单 NUL 是串分隔符，双 NUL 是"屏幕块结束"。某版回写把"译文短于原文"的差额用 **0x00** 填充、并把尾部全角空格也换成 0x00，导致池里出现 1~20 不等的任意长 NUL 段：

| 版本 | NUL 段长度分布 | 结果 |
|---|---|---|
| 原始 | `{1:358, 2:97}` | 正常 |
| 错误写回 | `{1:112, 2:52, 3:56, 4:6, 5:59, …, 20:2}` | 标签定位失败 → 文字空白 |
| 修正后 | `{1:358, 2:97}` | 与原始逐位置一致 |

现象是"按键图标在、文字空白"：图标（○×△□）走几何 / 符号字形区，不受影响；文字走字符串池定位，池结构坏了就定位不到。排查这种"图标在、文字空"时，若图标与文字共用同一字库，字库就基本没问题，应先查**字符串定位 / 池结构**。

### 3.2 正确的填充方式

等长替换 + 填充用**全角空格 0x8140**，而不是 0x00，并且结尾 NUL 一个都不碰：

```python
# 译文写入后，用全角空格填满原内容区 [start, nul_idx)，结尾 NUL(s) 原样保留
pad = content_len - len(enc)
p = start + len(enc)
while pad >= 2:
    out[p] = 0x81; out[p+1] = 0x40; p += 2; pad -= 2
if pad == 1:          # 译文含半角 ASCII（如 RGB/COM）导致差 1 字节
    out[p] = 0x20     # 用半角空格补齐（非 NUL 即安全）
```

- 偶数差用 0x8140（全角空格）；奇数差（译文含半角 ASCII）用 0x20（半角空格，只要非 NUL 就安全）。
- 结尾 NUL（单 / 双）完全不碰 → NUL 段结构与原始逐位置一致。

这条教训反过来说明：**逆向结论要原样落到实现**。"应填 0x8140"而实现写成了 0x00，一字之差就是空白 bug。

## 四、MES / MRB / 容器回写检查清单

### 4.1 三张必须同步的表

修改任何容器，回写后按以下清单逐项核对。

**压缩层（fsliblzs 头）**

| 字段 | 要求 |
|---|---|
| 0x10 总大小 | 含 0x2C 头，与重压后实际文件大小一致 |
| 0x24 解压后大小 | BE 端序；游戏据此分配缓冲 |
| 0x2B 压缩标志 | 部件数据不要写 1（raw 不被部件加载器支持） |
| 对齐 | 原版全部容器 total size 都是 16 的倍数；不补齐会导致装载器读不满整 quadword、尾部数据错（表现为任务无限加载） |

**容器层（BND）**

| 字段 | 要求 |
|---|---|
| 内层 BND 头 0x0C | 容器总大小；游戏据此判定数据区边界，追加数据后不更新会被判越界 |
| 内层 BND 条目表 | 每个条目的 offset / size；重定位或追加后必须同步 |
| 外层 BND 目录 | 同上；涉及 AC.BIN 层面的重定位，见 [05 · 打包与 ISO](05-packaging-and-iso.md) |

**文本层（.mes）**

`.mes` 结构：头部 0x10 + 条目表 count×16 + 子指针表 count×8 + 文本区；每行 UTF-16LE，以 `00 00` 结束。重建时：

- 更新条目表与子指针表里每个字符串的指针 / 大小。
- 行尾低半角字符转全角（原版行尾全角惯例，避免半角字符的高位 0x00 与 `00 00` 终止符相邻造成边界歧义）。
- 新数据追加到容器末尾并 16 字节对齐。

### 4.2 引用层与标识符层

- **偏移 / 索引引用**：STR 段这类被外部偏移引用的字符串，只能等长替换；要变长必须同步全部引用（见第二节）。
- **控件标识符**：MRB 里不只有显示文字，还有大量控件标识符（如 `Head_攻撃力`、`String_Param後`、`Warning_腕部重量過多`、`SpecBar_前`）。**这些标识符的日文部分也是标识符本身**，盲目全文件替换会把它改掉 → 游戏找不到控件 → 界面崩溃。只有纯显示标签（如 `Head_*` / `String_*` 属性名）需要改，且必须与属性类别标签逐字一致（含简体、全半角、后缀）。
- **显示标签 ≠ 状态键**：同一段文字可能同时以"状态键"和"显示标签"两种身份出现（名字输入页签就是一例）。改之前先确认渲染源，别把状态键当显示文本改。

### 4.3 一个等长替换的正面示例

名字输入页签（かな / カナ / 英数 / 漢字 / 記号）的渲染源是 `NameEntry.mrb` / `NameEntry2.mrb` 的对话框块，而不是某个全局字符串池。结构实测：

- 每个 .mrb 内 3 块，每块 5 个标签，块内按固定顺序排列，标签间隔 **0x30**。
- 每条 0x30 记录里，标签字段在 **+0x18** 处，格式为 **4 字节 SJIS + 4 字节 0x00**。
- 等长替换即可：把标签按码表逐字换成已注入字形的中文码，并全部核对落在字库区间表内。

反面教训：曾按旧笔记去改另一处字符串池里的"同名短标签"，结果页签显示不变、还连带内置键盘空白——因为那里其实是状态机键，不是渲染源。"改了没反应"这个信号本身就是在提醒：改的不是渲染源。

## 坑与教训

### 坑 1：重压 5xxxx → 机库 3D 预览贴图损坏

- **现象**：机库 3D 预览里若干部件贴图损坏，进任务 / 测试场后同一部件正常；描述文字始终正常。
- **根因**：把 5xxxx（模型 + 贴图二进制）也解压→重压；而 5xxxx 的描述从没被机库显示，描述文字其实由 6xxxx 提供。
- **规避**：只翻译 6xxxx（描述文字），5xxxx 保持原版压缩不动。排查回写 bug 时用二分法，把"改内容 / 重压缩 / 搬位置"三个变量逐个还原。

### 坑 2：0x00 填充 → 按键说明文字空白

- **现象**：机库底部按键说明栏"按键图标在、文字空白"。
- **根因**：短译文的差额用 0x00 填充，破坏了池的 {单 NUL, 双 NUL} 结构。
- **规避**：差额用 0x8140（全角空格，奇数差用 0x20），结尾 NUL 原样保留；回写后校验 NUL 段分布与原始一致。

### 坑 3：盲目替换 MRB → 机库打不开

- **现象**：对 Assembly*.mrb 做全文件 2 字节替换后，机库打不开。
- **根因**：`Warning_*` / `String_Param*` / `SpecBar_*` 等控件标识符的日文部分是标识符本身，被替换后失配。
- **规避**：先区分"显示文字"与"标识符"；只对纯显示标签做等长替换，并保证与匹配表逐字一致。

### 坑 4：变长替换 STR 段 → 进机库卡死

- **现象**：对 MRB STR 段做变长替换 + 段尾 NUL 补齐后，进机库卡死。
- **根因**：字符串被外部偏移 / 索引引用，变长移位了后续字符串。
- **规避**：默认只做等长替换；变长必须先逆向引用结构并同步全部引用。

### 坑 5：改了没反应 → 改错渲染源

- **现象**：改字符串池里的名字输入页签标签，页签显示不变，内置键盘还空白。
- **根因**：真正渲染源是 .mrb 对话框块；字符串池里那条是状态机键。
- **规避**：改动前先验证渲染源（字节搜索所有同名副本 + 看结构）；"改了没反应" = 改的不是渲染源。

### 坑 6：往返无损自测通过，游戏仍然出错

- **现象**：自写压缩器 round-trip 逐字节一致，装进游戏仍出现贴图损坏 / 无限加载。
- **根因**：自测只证明自洽，不证明游戏兼容；后经逆向确认 LZSS 算法本身与游戏一致，坏因更可能在目录 / size 同步层（引 [01 · 解包](01-unpacking.md)）。
- **规避**：把"压缩算法正确"和"容器字段同步正确"当作两件独立的事分别验收；对齐、size、目录项缺一不可。
