# 01 · 解包：从 PS2 镜像逐层拆到文本容器

一句话定位：本文给出一条可复刻的技术路线，从《Armored Core: Last Raven》的 PS2 光盘镜像出发，经 ISO9660 文件系统、AC.BIN 主归档、BND 目录、fsliblzs 压缩流，最终拿到可分析、可回写的文本容器（.mes / .dat / .mrb 等）。

## 背景与目标

ACLR 把几乎全部游戏资源塞进一个主归档 **AC.BIN**。要做文本翻译、字体替换或资源分析，第一步不是去改内容，而是先独立走通这条数据链：

```
ISO9660 光盘镜像
  └─ AC.BIN                         顶层 BND 归档
      ├─ 条目（fsliblzs 压缩容器）→ 解压后可能是内层 BND
      │    └─ 内层 BND → 文本容器（.dat / .mes / .mrb …）
      ├─ 条目（未压缩，直接是数据）
      └─ 大条目（内部再嵌 offset/size 表 + 路径表，索引多个嵌套 BND，如字体包）
```

本文目标读者是只有正版镜像和 Python 3 的人：照着下面的格式说明与伪代码，能把「二进制 → 文本容器」这条链路独立复现，而不必依赖任何现成工具包。

## 前置依赖

- **Python 3**：只用标准库即可；本文给出可直接参考的解压与解析伪代码。
- **正版光盘镜像（ISO）**：自备。本文不提供、也不指导获取任何游戏文件或字体。
- 一个能读 **ISO9660** 的通用归档工具（仅用于把 AC.BIN 从镜像里导出，可选，任何支持该文件系统的工具都行）。

## 第 0 步：从 ISO 提取 AC.BIN

PS2 光盘镜像通常是 ISO9660 文件系统。AC.BIN 是其中的主数据归档，具体所在路径因版本而异，需自行在镜像文件列表中确认后导出。

顺带一提：光盘上的**主程序 ELF**（不同地区/修订版的版本串与偏移不同，以自己镜像中的为准）是验证解压器的最佳材料。实测本版本中游戏只有一个 fsliblzs 解压器，位于文件偏移 **0x1AA220**。本文第二步与第三步的算法结论（窗口、dist 语义、结束标记等）均由该函数反汇编 + 与参考实现逐字节比对得来；其他地区版/修订版偏移可能不同，需自行确认。

如果要**修改 ELF 里的常量**（例如汉化后字库超出了游戏预留的内存区，必须把它搬走），会用到 VA ↔ 文件偏移的映射：按程序头算，`文件偏移 = VA − (p_vaddr − p_offset)`。本作主程序 ELF 的 text 段是 `p_offset=0x100 / p_vaddr=0x100000`，故 **文件偏移 = VA − 0xFFF00**（用近似值会整体差 `0x100`，拿到的指令全是错的）。相关做法与改 ELF 的副作用见 [08 · 字库容量与 ELF 补丁](08-font-capacity-and-elf-patching.md)。

## 第 1 步：AC.BIN 顶层 BND 解析

AC.BIN 是一个 BND 归档：

| 偏移 | 长度 | 含义 |
|---|---|---|
| 0x00 | 4 | 魔数 `BND\0`（`42 4E 44 00`） |
| 0x00–0x1F | 32 | 头部（含魔数；其余字段本文解包用不到） |
| 0x20 起 | 每 16 字节一槽 | 目录表，直到数据区起点 |
| 数据区 | — | 各子文件的真实字节 |

目录槽为 16 字节，字段全部**小端**：

```
struct dir_entry {        // 顶层 AC.BIN
    u32 id;               // 条目 ID
    u32 offset;           // 相对整个 AC.BIN 的字节偏移
    u32 size;             // 字节数
    u32 flags;            // 本层未用到
};
```

实测本版本数据区起点为 **0x13800**（目录表从 0x20 一直铺到数据区起点，约 5000 个槽，具体条数因版本而异）。更稳妥的做法不是硬编码该值，而是扫描目录、把第一个「offset 合理且 offset+size 不越界、size>0」的槽当作数据区起点，再在 [0x20, 数据区起点) 区间内逐槽收集有效条目。

一个实测示例：本版本存在大条目 `id=0x12C, offset=0x90C800, size=0x42BD370`（约 70 MB），字体资源就藏在它内部（见第 3 步末尾「嵌套：大条目里再嵌一层」一节）。

## 第 2 步：fsliblzs 解压

许多 BND 条目本身又是一个 `fsliblzs` 压缩容器，需要先解压。文件头布局如下：

| 偏移 | 长度 | 含义 |
|---|---|---|
| 0x00 | 8 | 魔数 `fsliblzs`（未压缩原样另有 `rawdata` 魔数，由上层分派） |
| 0x10 | 4 | 文件总大小（LE，含 0x2C 字节头） |
| 0x14 | 4 | 压缩标志（LE，=1） |
| 0x20 | 4 | 窗口大小提示；实测原版样本恒为 256（`0x00000100`），但**游戏解压器不读它** |
| 0x24 | 4 | 解压后大小（**BE**，仅 raw 分支使用） |
| 0x2B | 1 | raw 标志；==1 时走「未压缩原样复制」分支（游戏中几乎不用） |
| 0x2C | — | LZSS 压缩流起点 |

几个反汇编确立的关键事实：

- **0x20 字段被忽略**：解压器只读 0x2B（raw 标志）与 0x24（仅 raw 分支）；压缩路径连 0x24 都不读，只靠流内结束标记停止。0x20 写成 0 或 256，解压结果完全相同。合理推断它是「以 16 字节为单位的窗口大小提示」（256×16=4096=0x1000），但游戏把窗口硬编码、忽略该字段。
- **窗口 = 0x1000（4096）**，硬编码。
- **dist 相对窗口起点**：`src = max(0, 当前输出长度 − 0x1000) + dist`，不是相对当前位置往回数。
- **length = nibble + 1**（1..16，最大 16）。
- **结束标记 = `length nibble == 0`**（游戏只看 nibble，不看 dist）。

LZSS 流采用 flag 字节制，**位序 LSB 优先**：每 8 个操作一组，组前一个 flag 字节；flag 的 bit0 对应第 1 个操作，bit1 对应第 2 个，……bit7 对应第 8 个。

- flag 位 = 0 → 字面量，直接透传 1 字节。
- flag 位 = 1 → 回引 token，2 字节 `[b1, b2]`：
  - `dist   = (b1 << 4) | (b2 >> 4)`（12 位）
  - `nibble = b2 & 0xF`
  - `length = nibble + 1`
  - `src = max(0, pos − 0x1000) + dist`，逐字节复制。

参考伪代码（等价于游戏算法，重叠匹配逐字节复制、安全）：

```python
WINDOW = 0x1000

def decompress(blob, stream_off=0x2C):
    assert blob[:8] == b'fsliblzs'
    if blob[0x2B] == 1:                     # raw 分支，几乎不用
        size = int.from_bytes(blob[0x24:0x28], 'big')   # BE 解压后大小
        return blob[stream_off:stream_off + size]       # raw 起点见「坑与教训」第 9 条
    out = bytearray()
    i, flag, bit = stream_off, 0, 0
    while i < len(blob):
        if bit == 0:
            flag, i, bit = blob[i], i + 1, 0x01       # LSB 优先
        if flag & bit:
            b1, b2 = blob[i], blob[i + 1]
            i += 2
            dist  = (b1 << 4) | (b2 >> 4)
            nibble = b2 & 0xF
            if nibble == 0:                 # 结束（游戏只看 nibble）
                return bytes(out)
            length = nibble + 1             # 1..16
            base = len(out) - WINDOW
            if base < 0:
                base = 0
            src = base + dist               # 相对窗口起点
            for _ in range(length):         # 逐字节，重叠安全
                out.append(out[src]); src += 1
        else:
            out.append(blob[i]); i += 1
        bit <<= 1
        if bit == 0x100:
            bit = 0
    return bytes(out)
```

> 说明：某些参考实现把结束标记判成 `dist==0 且 nibble==0`（即 `00 00`）；游戏只判 `nibble==0`。实测合法流里不存在 `nibble==0 且 dist≠0` 的 token，两者在真实数据上等价。

## 第 3 步：内层 BND 与路径表

解压后的数据若以 `BND\0` 开头，就是内层 BND（任务容器、字体包等）。内层与顶层字段语义**不同**：

| 偏移 | 长度 | 含义 |
|---|---|---|
| 0x00 | 4 | 魔数 `BND\0` |
| 0x10 | 4 | 文件数（LE） |
| 0x20 起 | 每 16 字节一槽 | 文件表，共「文件数」条 |
| 路径表 | — | 从首条目的 path_offset 开始的 NUL 结尾字符串序列 |

内层文件表槽：

```
struct inner_entry {
    u32 id;               // 子文件 ID（同时是路径表下标）
    u32 offset;           // 子文件字节偏移
    u32 size;             // 字节数
    u32 path_offset;      // 指向路径表中的字符串
};
```

路径表解析：从首条目的 `path_offset` 起，按 `0x00` 断句，依次读出一串 **ASCII** 路径名，第 `i` 个字符串对应 `id==i` 的子文件。把每个子文件 `dec[offset:offset+size]` 切片落盘，`.dat / .mes / .mrb` 等就是文本容器（其中 **MES 是明文文本**）。

### 嵌套：大条目里再嵌一层

字体等资源往往**不是顶层条目**。实测本版本中，大条目 `id=0x12C`（`offset=0x90C800`）内部再嵌一层索引：路径表是字符串区，其后跟着 16 字节一槽的 `{id, offset, size, name_offset}` 表，offset 相对大条目数据起点（0x90C800）。据此能找到 `font.bnd` 这样的嵌套 BND；该字体包实测有 7 份副本，仅第 1 份被实际加载，其余是开发期备份。`font.bnd` 内部又是标准内层 BND：头部 0x20、目录 10 条、其后一段残留开发路径字符串（垃圾）、数据区从 0x210 起。

所以「层层下钻」时要注意：**子文件 offset 的基准随层不同**——任务容器这类内层 BND 的 offset 直接相对解压后缓冲；大条目内部的表则相对大条目数据起点。每钻一层都要核对基准。

## 一条可复刻的路线（端到端）

1. 用能读 ISO9660 的工具，把 **AC.BIN** 从镜像导出（路径因版本而异，自行确认）。
2. 解析顶层 BND 目录，得到 `{id: (offset, size)}` 条目表（见第 1 步伪代码思路）。
3. 对每个条目切片 `blob[offset:offset+size]`；若前 8 字节是 `fsliblzs`，用第 2 步解压。
4. 解压结果若以 `BND\0` 开头，按第 3 步解析内层文件表与路径表。
5. 把子文件按路径名落盘；`.mes`（明文文本）、`.dat`、`.mrb` 等就是文本容器。
6. 找不到字体/字库时，检查大条目（如 `id=0x12C`）内部是否还有 offset/size 表 + 路径表，再往下钻一层。

## 坑与教训

**1. 头部 0x20 字段改不改都一样**
- 现象：在头部 0x20 处看到 `256`，怀疑「256 vs 0」决定解压是否成功。
- 根因：反汇编证实游戏解压器（本版本 0x1AA220）完全不读 0x20；窗口 0x1000 硬编码，压缩路径连 0x24 都不读，只靠流内结束标记。
- 规避：不要在 0x20 上做兼容性判断；解压只看魔数、0x2B、0x24（raw）、流内标记。

**2. dist 相对窗口起点，不是相对当前位置**
- 现象：照常见 LZSS 把 dist 当「往回数多少字节」，解出的数据错位。
- 根因：源地址 = `max(0, 当前输出长度 − 0x1000) + dist`。
- 规避：严格按该公式取源，不要用「当前位置 − dist」。

**3. 结束标记只看 nibble==0**
- 现象：参考实现要求 `dist==0 且 nibble==0` 才结束，游戏只看 nibble。
- 根因：游戏代码对 `b2 & 0xF` 判 0 即返回，不检查 dist。
- 规避：合法流里不存在 `nibble==0 且 dist≠0` 的 token，两者在真实数据上等价；写解析器时想清楚采用哪种判定，勿混用。

**4. 重叠匹配必须逐字节复制**
- 现象：`dist < length` 时（RLE 类回引）若整段 memcpy 会复制出错。
- 根因：解压器的快速路径（长度 ≥9 的 8 字节展开）也是「读一个写一个」的逐字节顺序。
- 规避：实现时逐字节 copy（`out.append(out[src]); src += 1`）。

**5. 目录槽不是全有效，数据区起点要自动探测**
- 现象：目录区里夹着 `size==0` 或 offset/size 越界的空槽。
- 根因：目录是从 0x20 到数据区起点的 16 字节槽序列，部分槽为空。
- 规避：逐槽过滤；数据区起点取第一个「offset 合理且 size>0」的槽（本版本实测 0x13800），不要硬编码条数。

**6. 顶层与内层 BND 字段语义不同**
- 现象：用同一套解析器套两层，第 4 字段解读错、路径名成乱码。
- 根因：顶层槽是 `{id,offset,size,flags}`（flags 未用）；内层槽是 `{id,offset,size,path_offset}`，且内层在 0x10 有 u32 文件数，顶层靠扫描。
- 规避：两层分开解析，别共用字段假设。

**7. 路径表是 NUL 结尾字符串序列**
- 现象：把路径表当固定长度字段会读串。
- 根因：路径表从首条目的 path_offset 开始，是一串以 0x00 分隔的 ASCII 字符串，按条目 id 下标取用。
- 规避：读到 0x00 断句、逐条累积，再按 id 索引。

**8. 字体等资源不在顶层，要再往下钻一层**
- 现象：在外层目录里找不到 font.bnd / 字库文件。
- 根因：字体塞在大条目（本版本 `id=0x12C`）里，其内部用 offset/size 表 + 路径表索引出多个嵌套 BND（font.bnd 有 7 份副本，仅 1 份被加载）。
- 规避：对大条目检查是否内含 BND/路径表结构，逐层下钻；注意子文件 offset 的基准随层不同。

**9. rawdata 分支的起点因实现而异**
- 现象：`0x2B==1` 的 raw 文件，不同实现读出的数据偏移不一致。
- 根因：参考实现从 0x30 取数据，游戏反汇编显示从 0x2C 取，两者与样本实际布局（真数据在 0x30）也不完全一致。
- 规避：raw 文件极罕见（原版仅个别样本）；真要处理 raw 路径时，以样本实测核对起点，不要盲信任一实现。压缩路径不受影响。

**10. 解压器没有越界 / 死循环保护**
- 现象：非法或截断的流可能越界读、甚至死循环。
- 根因：游戏解压器不校验 dist 上界与输出上限，输出缓冲大小靠调用方按 0x24（BE）大小预先分配。
- 规避：自己实现时加 `src < len(out)` 检查与步数上限；解析目录时也始终校验 `offset+size` 不越界。
