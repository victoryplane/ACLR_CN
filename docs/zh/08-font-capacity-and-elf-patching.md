# 08 · 字库容量与 ELF 补丁：当「数据全对」也救不了字形

> 本篇讲的是一类最难查的字形损坏：**字库文件本身逐字节正确、16 字节对齐也对、上传与采样代码也没错，
> 但某些字在画面上就是坏的，而且「坏的到底是哪几个字」还会随场景变化。**
> 根因不在文件里，而在**游戏给字库预留的 RAM 缓冲区装不下我们的字库**——多出来的那截字形
> 落在引擎自己的 RAM 里，被引擎每帧写的数据盖掉，上传时被忠实抄进了显存。
>
> 本篇给出定位手段（从即时存档里取出字库的运行时副本，与 ISO 逐字节比对）、修法
> （把字库搬出预留区 + 改 ELF 里的两个常量），以及**改 ELF 之后必须记得处理的副作用**：
> 模拟器的 game CRC 变了，以 CRC 命名的 per-game 设置与补丁会全部失配。

## 背景与目标

《03 · 字库与渲染》给出的约束是「结构正确 + 16 字节对齐」；本篇补上**第三条硬约束：
容量**。三者的关系可以这样记：

| 约束 | 违反后的表现 | 坏的规模 |
|---|---|---|
| 结构 / 字节序 / tail 寻址 | 字形串位、镜像、压扁 | 涉及的具体字形 |
| 16 字节对齐 | 上传后**全体**字形错乱、融化 | 整库 |
| **容量（本篇）** | 只有**超出预留区的那几个槽**坏，且**随场景变化** | 一个「溢出边界」之后的所有槽 |

本篇目标：让你遇到「数据全对、对齐也对、却有个别字坏，而且换一关坏的字就变了」时，
有一套**能出判决性证据**的排查路径，以及一个**不改译文、不缩字库**就能根治的修法。

## 前置依赖

- 按《01 · 解包》《03 · 字库与渲染》已能提取并重建目标字库（本篇以 ACLR 的 `0A93` 局内对话字库为例）。
- **模拟器的即时存档**（PCSX2 的 `.p2s`）——这是本篇的主证据来源，不需要调试器、不需要断点。
- Python 3 + 标准库 `zipfile`；解 zstd 需要 `zstandard`（第三方包）。
- 目标游戏的主程序 ELF（自备镜像中提取），以及一个**能对 MIPS 小端反汇编**的工具。

## 一、先判断症状属于哪一类

三类问题的现象高度相似，但混起来查会浪费大量时间。先用这张表定位方向：

| 现象 | 更像哪一类 | 第一件该做的事 |
|---|---|---|
| 某个字**整体模糊**、发灰、有毛刺，但结构没坏 | 渲染/量化（见 03 §五 CLUT） | 用纹理转储反推真实 CLUT，按亮度最近匹配 |
| **全部**字形错乱、融化、串位，数据却全对 | 对齐 / 布局（见 03 §八） | 查位图偏移 mod 16、`interleaved` vs `linear` |
| **只有几个字**坏（缺笔画、上半截错位、像被别的数据糊住），**换关卡/换场景坏的字就变了** | **容量溢出（本篇）** | 从即时存档取字库副本，与 ISO 逐字节比对 |

最后一行有两条**极有特征**的线索，看到就该往这个方向想：

1. **同一个字在不同场景下坏法不同**，甚至同一场景里有的字好、有的字坏；
2. **把文本改一改，坏的位置并没有跟着文本走**——坏的是「某个字形槽」，不是「某段文本」。

> 补充一条边界：并非所有「单字损坏」都属于容量问题。本项目另一个字（`〇`）坏在
> **字形数据本身与 CLUT 亮度档不匹配**（槽里的位图 nibble 用的档位与周围字形不同，
> 亮度落在暗档上，看起来就是缺笔画），那属于渲染/数据问题，对症下药是**重画那个槽**。
> 所以本篇的判据不是「单字坏」，而是**「坏的位置随场景漂移」**。

## 二、第一步：从即时存档里取出字库的运行时副本

PCSX2 的 `.p2s` 是一个 **ZIP 容器**，其中 `eeMemory.bin` 是 EE 主内存（32 MB）的快照，
成员用 **zstd** 压缩（ZIP 里 method = 93，Python 3.14 之前的标准库不认，需要手动解）：

```python
import io, struct, zipfile, zstandard

def read_ee_ram(p2s_path):
    """从 .p2s 即时存档里解出 32 MiB 的 EE 主存镜像。"""
    with zipfile.ZipFile(p2s_path) as z:
        info = z.getinfo('eeMemory.bin')      # 成员用 zstd 压缩（ZIP method = 93）
        try:
            return z.read(info)               # Python 3.14+：标准库原生支持 zstd
        except NotImplementedError:           # 更早的版本：自己取压缩数据交给 zstandard
            with open(p2s_path, 'rb') as f:
                f.seek(info.header_offset)
                nlen, elen = struct.unpack_from('<HH', f.read(30), 26)
                f.seek(info.header_offset + 30 + nlen + elen)
                raw = f.read(info.compress_size)
    with zstandard.ZstdDecompressor().stream_reader(io.BytesIO(raw)) as r:
        return r.read()

ram = read_ee_ram(r'...\SLPS-25462 (XXXXXXXX).01.p2s')
print(len(ram))                               # 33554432 = 32 MiB
```

拿到 RAM 镜像后，**在 RAM 里找字库的运行时副本**。最省事的定位器是字库自己的
**区间表字节**（取 ISO 字库里区间表的前若干字节，直接 `ram.find(...)`）：

```python
ram_off = ram.find(iso_font[0x40:0x40 + 32])       # 区间表开头 32 字节
print(hex(ram_off))                                # 例：本作实测 0x1C03150
```

这一步顺带解决了另一个关键问题：**字库被加载到了哪个固定地址**——
本作实测三次不同会话、不同日期都是 `0x1C03150`，这个地址后面要用。

## 三、第二步：与 ISO 里的字库逐字节比对（主判据）

把 RAM 里的副本切出来，与 ISO 里的字库逐字节比对，**统计「连续差异段」**，而不是只数差异字节：

```python
n   = len(iso_font)
cpy = ram[ram_off:ram_off + n]
runs, start = [], None
for i in range(n):
    if cpy[i] != iso_font[i]:
        if start is None:
            start = i
    elif start is not None:
        runs.append((start, i)); start = None
if start is not None:
    runs.append((start, n))
print(runs[:10], '总差异段数 =', len(runs))
```

本项目实测结果（这就是「判决性证据」）：

```
0x29000 以下  ：完全干净（逐字节相同）
第一个差异字节：0x29002   （0x29000 正是第 1025 个字形的起点）
0x29000 之后  ：一路到字库末尾都有差异段（共 61 段 / 1,078 字节不同）
                差异段并不连续——覆盖进来的数据偶尔与被覆盖的字节相同，
                但「边界以下一个字节都没动」这一点是决定性的
```

本仓的工具可以把这套判断直接跑出来：

```bash
# 1) 这份数据被加载到哪个地址？（实测输出：file base address = 0x1C03150）
python tools/savestate_ram.py locate "<存档>.p2s" font.bin --at 0x40 --len 32

# 2) 与内存副本逐字节比对；--from 跳过「加载后被改写成绝对地址」的头部指针区
python tools/savestate_ram.py diff "<存档>.p2s" font.bin --addr 0x1C03150 --from 0x8F80
#    补丁前 → 差异段从 0x29002 起、一路到末尾
#    补丁后 → 0 段、0 字节（完全一致）
```

> **一个容易误判的细节**：容器被加载到内存后，头部的「文件内偏移」指针会被游戏改写成
> **运行时绝对地址**。所以整文件比对时，开头（本例 `0x20..0x34` 那几个指针字段）**总会有**
> 一小段差异——那不是损坏。判断「有没有被覆盖」要看**数据区**，用 `--from` 跳过头部即可。

**关键结论：损坏不是随机的，而是从字库内偏移 `0x29000` 开始、一刀切到底。**
一个「文件内偏移」的硬边界，说明问题不在字形数据、不在文本、也不在渲染器，
而在**游戏把字库放在了一个大小有限的缓冲区里**——边界之后的内容被别人的数据盖掉了。

同时它还解释了「为什么坏的字会变」：**越过边界的那些字形槽，谁被盖、盖成什么，
取决于当时引擎往那块 RAM 里写了什么**，所以逐帧/逐场景不同。

> 排查技巧：如果存档里找不到字库副本，先确认该界面**确实加载了**这套字库
> （同一份文本在不同界面可能走不同字库，见《07 · 调试与 MCP 断点》的「当前字体指针」一节）。

## 四、根因：字库超出了引擎预留的 RAM 缓冲区

把上面的边界换算成绝对地址，一切就串起来了（本作 `0A93` 实测值）：

```
字库加载地址   B = 0x1C03150        （固定，多次会话一致）
损坏起点        = B + 0x29000
紧随其后的引擎静态数据起点 E = 0x1C2C150 = B + 0x29000     ← 边界完全吻合
```

即：**游戏给这套字库预留的可用区只有 `0x29000` = 167,936 字节**，
紧接着就是引擎自己的数据（本项目里是一块 **512 字节**的结构，按「字库末尾」常量定位）。
而我们的汉化字库是 **190,976 字节**，超过了 23,040 字节 = **180 个字形槽**
（槽号按「位图内第几个字形」计，0 起；即第 1025 个字形之后的全部）。

为什么原版不会出问题？算一下容量就明白了：

| | 位图偏移 | 字形数 | 位图字节 | 字库总大小 | 是否超预留区（`0x29000`） |
|---|---|---|---|---|---|
| 原版 | `0x67E0` | 877 | 112,256 | 138,848 | ✅ 宽松（余 28 KB） |
| 汉化 | `0x8F80` | 1205 | 154,240 | 190,976 | ❌ **超 23,040 B** |

汉化用字比原版多，位图区一路往后长，**长过了游戏留给它的屋子**。

## 五、容量预算：先算清楚「上限是多少个字形」

这套预算可以在**动手补字之前**就算出来，避免白干：

```
位图可用字节 = E − (B + 位图偏移)              # E = 紧随字库的引擎数据起点
最多字形数   ≈ 位图可用字节 / 每字形字节数
```

本作代入：`E − B = 0x29000`，位图偏移 `0x8F80` ⇒
`(0x29000 − 0x8F80) / 128 = 131,200 / 128 = 1025` 个字形。

也就是说：**这套字库在原版游戏的内存布局里，最多只能放 1025 个字**（含 ASCII/符号）。
汉化需要 1205 个 ⇒ 有两条路：

| 方案 | 可行性 |
|---|---|
| A. 瘦身到 1025 字以内 | ❌ 本作不可行：仅「1035 个汉字 + 95 个 ASCII」就 1130 槽；合并区间表最多再挤出几十槽，仍不够 |
| B. **把字库搬出预留区**，并让引擎知道新的边界 | ✅ 可行，见下 |

> 这条预算对所有有「固定加载地址 + 紧跟其后别的数据」的位图字库都成立。
> 动手扩字库前先算一遍，比事后拿存档排查便宜得多。

## 六、一个便宜的判决实验：同位置换字

在改任何代码之前，先花十分钟做这个实验，把「内容问题」和「位置问题」彻底分开：

> 把**一个确定安全的槽**里的字形，与**一个确定受害的槽**里的字形**互换**（只换位图数据，文本不变）。

本项目实测结果：把 `满`（安全槽）的字形数据换到受害槽的位置，
**画面里坏的不再是原来那个字的位置，而是「那个槽」对应到的文本**；
反过来，把受害字节形放到安全槽，它显示正常。

**结论：受害由「字形槽 / 数据偏移」决定，与文本内容、与渲染器都无关。**
这与《05 · 打包与 ISO》里「把原版数据放到追加位置」是同一类二分思路——
**换一个变量，看现象跟着谁走。**

## 七、修法：把字库搬到 ELF 段之外

思路很直接：既然 `B + 0x29000` 之后就被引擎占用了，那就**换一个更宽敞的地方放字库**，
并且把 ELF 里那两个「字库基址」和「字库末尾」常量一起改掉。

### 7.1 先建立 VA ↔ 文件偏移的可靠映射

改 ELF 的前提是「知道某个虚拟地址在文件里的哪个偏移」。别按直觉近似，用程序头算：

```
文件偏移 = VA − (p_vaddr − p_offset)        # 对包含该 VA 的那个 LOAD 段
```

本作主程序 ELF 的 text 段是 `p_offset = 0x100`、`p_vaddr = 0x100000`，于是：

```
文件偏移 = VA − 0xFFF00
```

本仓 `tools/elf_addr.py` 可以直接打印出来：`info` 子命令列出所有 LOAD 段与各自的增量，
`map <ELF> <地址>` 告诉你某个 VA 属于「文件数据 / 仅运行时映射（BSS）/ 段外空洞」哪一类
——**挑搬迁落点时这条判断很重要**。

⚠️ **这条映射是排查过的坑**：早期有脚本用「按程序头自己拼」的写法，
结果整体差了 `0x100`（拿到的指令全是错的，还据此推出过错误结论）。
**统一用 `VA − 0xFFF00`，并且每次改 ELF 前先用它反查一句已知指令核对一遍。**

### 7.2 找出所有引用「字库基址 / 字库末尾」的位置

MIPS 里一个 32 位常量由 `lui` + `addiu` 拼出，所以在反汇编里搜这两个常量的**高低 16 位组合**，
就能把引用点找全（本仓 `tools/elf_addr.py find-const` 就是干这个的：它会把配对的
`addiu`/`ori` 一并找出来，并核对寄存器是否一致）。本作实测：

```
字库基址   0x1C03150 = lui 0x1C0 + addiu +0x3150     出现 4 处
字库末尾   0x1C2C150 = lui 0x1C3 + addiu −0x3EB0     出现 3 处
```

> 一个帮助记忆的点：MIPS 指令是定长 4 字节、**小端存储**，而 `lui` 的立即数正好占据指令字的低 16 位，
> 于是**立即数的低字节就是该指令在文件里的第一个字节**——「把 `lui 0x1C0` 改成 `lui 0x1D7`」
> 在十六进制编辑器里就是**改 1 个字节**（`C0` → `D7`）。`addiu` 的 16 位立即数同理占据字节 0–1
> （例如 `addiu ...,−0x3EB0` 编码为 `50 C1 xx xx`，改成 `+0x1B50` 就是 `50 1B xx xx`）。

### 7.3 选一个新的落点

新地址必须同时满足：

1. **落在 ELF 所有 LOAD 段之外**（不会和代码/数据段重叠）；
2. 是一块**实测没人用**的 RAM（靠存档比对 + 全流程试玩确认，别只看「这里好像是空的」）；
3. 尾部留出**完整字库大小**，且不与堆/栈的生长方向冲突。

本作选的新基址：`0x1D73150`（新字库要占 `0x2EA00` = 190,976 字节）。

### 7.4 补丁内容（本作实测：共 10 个字节）

> 下表的「VA」是虚拟地址；真实**文件偏移 = VA − 0xFFF00**（本作 text 段的增量），括号里一并给出。

| 组 | 作用 | 原值 → 新值 | VA（文件偏移） |
|---|---|---|---|
| A（4 处 `lui`） | 字库基址 | `0x1C03150` → `0x1D73150` | `0x24D764`(`0x14D864`)、`0x24DBB0`(`0x14DCB0`)、`0x24DBC8`(`0x14DCC8`)、`0x24DD08`(`0x14DE08`) |
| B（3 处 `lui`） | 字库末尾（引擎数据起点） | `0x1C2C150` → `0x1DA1B50` | `0x24D768`(`0x14D868`)、`0x24DBCC`(`0x14DCCC`)、`0x24DD0C`(`0x14DE0C`) |
| B（3 处 `addiu`） | 末尾常量的低 16 位 | `−0x3EB0`（`50 C1 A5 24`）→ `+0x1B50`（`50 1B A5 24`） | `0x24D778`(`0x14D878`)、`0x24DBD8`(`0x14DCD8`)、`0x24DD18`(`0x14DE18`) |

每个引用点只改 **1 个字节**（`lui` 改的是指令字的第一个字节；`addiu` 改的是第 2 个字节，
即文件偏移 `0x14D879` / `0x14DCD9` / `0x14DE19`），合计 **10 个字节**。

**但建议不要手改。** 用本仓工具一条命令生成：

```bash
python tools/elf_addr.py patch <未打补丁的ELF> 0x1C03150 0x1D73150 --out step1.elf
python tools/elf_addr.py patch step1.elf        0x1C2C150 0x1DA1B50 --out final.elf
```

它会自动找全引用点、判断哪些字节需要改（包括「新常量的低 16 位也变了，得连 `addiu` 一起改」），
并且**只写副本、绝不原地修改**。本项目最终版的 ELF 就是这条命令生成的——
产物与当初手工补丁的版本**逐字节一致**（md5 相同）。

**为什么必须连「末尾」常量一起改**——这是本项目踩过的第二个坑，值得单独记：

> 第一版搬迁**只动了「基址」和「末尾」的高 16 位**（4 处 `lui` + 3 处 `lui`），
> 也就是让末尾常量**跟着基址一起走、保持 `基址 + 0x29000` 的相对关系不变**（这是很自然的做法），
> 结果**还剩 4 个槽坏**。
> 原因：引擎那块 512 字节的数据是**按「字库末尾」常量定位**的，字库搬到哪儿它就跟到哪儿，
> 于是它落在了 `新基址 + 0x29000`——而新字库比 `0x29000` 大得多，
> 那块数据**正好落在新字库的肚子里**，继续盖住第 1025–1028 个槽。
> 把「末尾」改成**新字库自己的真实末尾**（`新基址 + 字库大小` = `新基址 + 0x2EA00`，
> 即再把 3 处 `addiu` 的低 16 位也改掉）之后，引擎数据落到字库**之后**，问题才彻底消失。

教训：**搬迁一个「基址 + 末尾」常量对描述的对象时，两个都要改，
并且要让「末尾」表达新对象自己的真实长度，而不是复用旧对象的边界。**

## 八、改 ELF 的副作用：模拟器的 game CRC 变了

**这一节是发行环节最容易翻车的地方，务必读完。**

模拟器在启动游戏时会算一个**游戏标识 CRC**（PCSX2 在 `pcsx2/Elfheader.cpp` 的 `GetCRC()` 里做这件事）。
本项目实测其算法：

```
CRC = 整个 ELF 文件的 32 位小端字，逐字 XOR（尾部不足 4 字节忽略）
```

> 说明：本作 ELF 长度是 4 的倍数，所以「尾部怎么处理」不影响结果；
> 换别的游戏时，**以模拟器实际显示的 CRC 为准**（游戏列表/日志里能看到），
> 上面的算法只用来**预测**打完补丁后会变成什么值。
> 另外这是模拟器的实现细节，不同版本可能不同——本项目的做法是：
> 用「未打补丁的 ELF」验证一遍算法，确认算出来的值等于模拟器显示的值，再拿它去预测新值。

实测三个值（同一游戏，只有 ELF 的 10 个字节不同）：

| 版本 | ELF 补丁 | game CRC |
|---|---|---|
| 未打补丁（`最终修复96` 及之前） | 无 | `FEBE1992` |
| 第一版搬迁（`最终修复98`） | 7 处（基址 4 + 末尾的**高** 16 位 3，末尾仍等于「基址 + 0x29000」） | `FEBE198B` |
| 最终版（`最终修复99`） | 4 处基址 + 6 处末尾 | `FEBEC38B` |

**改 ELF 会让 CRC 变**，而模拟器的这两类东西**是按 CRC 命名的**：

- **per-game 设置**：`gamesettings\<序列号>_<CRC>.ini`
- **内建补丁**：`patches\<序列号>_<CRC>.pnach`（补丁库在模拟器安装目录的 `resources\patches.zip` 里）

（**游戏数据库 GameDB 是按序列号索引的**，不受影响。）

于是用户侧会出现一个很奇怪的现象：**「以前能勾选的那些补丁，现在列表是空的」**——
不是补丁丢了，而是「抽屉的标签换了，抽屉里的东西还在原来的标签下」。

**处置**（思路三步 + 本仓一条命令）：

```bash
python tools/pcsx2_crc.py <ISO> --install --data "<PCSX2 数据目录>" \
       --prog "<模拟器安装目录>" --old-crc FEBE1992
```

```python
# 1. 从 ISO 里取出主程序 ELF，算 CRC
crc = 0
for i in range(len(elf) // 4):
    crc ^= struct.unpack_from('<I', elf, i * 4)[0]

# 2. 把旧的 per-game 设置复制成新 CRC 的名字
shutil.copyfile(f'gamesettings/{SERIAL}_FEBE1992.ini', f'gamesettings/{SERIAL}_{crc:08X}.ini')

# 3. 从模拟器的 resources/patches.zip 里取出本游戏的内建补丁，写成新名字
#    patches/<SERIAL>_<CRC>.pnach
```

**发行纪律**：只要 ELF 被动过，就必须把**按新 CRC 命名的那两份配置**（`*.ini` + `*.pnach`）
连同镜像一起发给测试者，否则他们看到的是「补丁列表空、设置没生效」。
CRC 只取决于 ELF，所以**之后只重做 `AC.BIN`/字库而不再动 ELF，CRC 保持不变**，
这套配置可以一直沿用。

## 九、验收清单（改完 ELF 后逐项过）

用**新存档**（打过补丁的 ISO 里新存的即时存档）跑，全绿才算修好：

| 项 | 检查 |
|---|---|
| V1 | 新基址处能解出一个**完整的字库头**（`size`/区间数/字形数/各指针自洽） |
| V2 | 四个重定位指针 == 新基址 + 原偏移（证明指针被正确改写成新基址的相对偏移） |
| V3 | **旧基址处不再有字库头**（证明真的搬走了，不是复制了一份） |
| **V4** | **RAM 里字库副本与 ISO 字库的位图区差异段 = 0**（**主判据**：引擎再也不改写字形） |
| V5 | 抽查曾经受害的字形槽，逐字节等于 ISO |

V4 是唯一真正说明「问题被根治」的判据：其余项只能证明「搬对了地方」，
只有 V4 能证明「**再也没人覆盖它**」。本项目最终实测：V1–V5 全通过、位图区差异段 = 0，
用户侧实机确认受害字恢复正常。

V4 也是这套工具里最容易复现的一条：

```bash
python tools/savestate_ram.py diff "<补丁后的存档>.p2s" font.bin --addr 0x1D73150 --from 0x8F80
# → [IDENTICAL] this range matches completely: nothing has overwritten it.
```

> 反向验证同样重要：拿**旧存档**（补丁前的即时存档）跑同一套检查，应当**正确地报「未通过」**
> （旧基址还有字库头、受害槽仍被改写）。脚本能区分补丁前/后，结论才可信。

## 十、坑与教训

1. **个别字坏、坏的字随场景变** → 字库超出游戏预留的 RAM 缓冲区，越界部分被引擎数据覆盖 →
   从即时存档取字库副本与 ISO 逐字节比对，看差异**是否从一个固定文件偏移一刀切开始**；
   算容量预算（`末尾常量 − 基址 − 位图偏移`）后再决定扩字库或搬字库。
2. **以为「对齐对了就万事大吉」** → 对齐只是 DMA 上传的要求，**容量是另一条独立约束** →
   扩字库前先算「最多能放多少个字形」。
3. **搬家只改了基址，还剩几个槽坏** → 引擎按「末尾」常量定位的一小块数据跟着搬进了新字库内部 →
   搬迁「基址 + 末尾」常量对时，**末尾要表达新对象自己的真实长度**。
4. **按程序头手算 VA→文件偏移，差 0x100** → 映射实现错误，读到的是错位指令，据此得出错误结论 →
   统一 `文件偏移 = VA − (p_vaddr − p_offset)`；本作即 `VA − 0xFFF00`，每次改前反查一句已知指令核对。
5. **改完 ELF 后用户报「补丁列表空了」** → game CRC 变了，per-game 设置与补丁按 CRC 命名 →
   算新 CRC，把 `*.ini` / `*.pnach` 复制成新名字，并**随发行包一起交付**。
6. **全零 ≠ 空闲（改 ELF 版）** → 选了「看起来没人用」的 RAM 落点 → 必须用实测（存档比对 + 全流程试玩）
   确认该地址区间无人使用，别只看零字节。
7. **只验证「搬对了」就发布** → V1–V3 只证明搬对了地方，不能证明没人再覆盖它 →
   必须以「RAM 副本 vs ISO 位图区差异段 = 0」作为主判据，并用旧存档做反向验证。
8. **整文件比对时开头总有几个字节不一致，被误当成损坏** → 容器加载后头部的「文件内偏移」指针
   被游戏改写成运行时绝对地址 → 比对时用 `--from <数据区起点>` 跳过头部，只看数据区。
9. **`.p2s` 解不开（`zipfile` 报 method 93）** → 成员是 zstd 压缩，旧版标准库不支持 →
   装 `zstandard`；或直接用本仓 `tools/savestate_ram.py`（它自己按本地文件头取压缩数据再解）。
