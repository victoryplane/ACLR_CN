# 07 · 调试与 MCP 断点：让 AI 操控模拟器做动态逆向

> 本文讲的是「方法」。当静态反汇编走到尽头，如何让 AI 借助模拟器的调试接口
> （GDB 调试桩、调试服务器，或封装成 MCP 工具的形式）下断点、抓寄存器、导内存，
> 把逆向推进到静态永远到不了的地方。
> 本文只描述方法论与适用场景，不提供、不捆绑任何调试工具或 MCP 实现，
> 对应工具请读者自备、自行获取。

## 为什么有效：AI + 动态断点的组合价值

静态反汇编能覆盖大量代码，但有天然盲区：

- **间接调用追不动**：PS2 游戏大量使用 `jalr`（寄存器跳转）和虚函数表间接调用，
  调用目标往往要到运行时才知道；有些虚表甚至位于 BSS 区，运行时才被填充，静态读不到。
- **真值只在运行时存在**：例如「当前正在用的字体对象指针」这类全局状态每帧都可能切换，
  静态分析只能看到读写它的指令，看不到它此刻实际等于多少。
- **部分数据运行时才生成**：例如字体 CLUT（颜色查找表）可能是运行时算出来的，
  静态反汇编里找不到完整表。

AI 的价值在于：它能通读大段反汇编、理解调用链、提出可证伪的假设，
并算出「验证这个假设需要读哪个寄存器、哪个内存地址、在哪个函数下断点」。
当这些调试动作被封装成 AI 可以直接调用的接口（典型如 **MCP，Model Context
Protocol，模型上下文协议**）时，AI 就能独立完成一个闭环：

**下断点 → 命中 → 读寄存器/内存 → 对比预期值 → 修正断点条件 → 再试。**

动态断点在这里扮演的角色是「证伪器」：静态分析只能列出若干「可能的链路」，
一次动态命中就能把「可能」压成「事实」——当前跑的是哪个字体对象、这个函数实际
返回了什么、这张纹理最后画成了什么。三者齐了就闭环。

这一循环把逆向从「人肉猜 + 改文件 + 重启验证」的慢速试错，变成
「连续多轮的快速求证」。更重要的是它可重复、可追溯：每次命中的寄存器值
都是客观证据，能直接写进结论，避免「感觉像」的猜测。
实际项目中，很多静态挖了很长时间仍无解的难题，动态断点几轮就收敛到真凶。

## 前置条件

- **PS2 模拟器**（如 PCSX2 类）自备，并能正常运行目标游戏。
- **调试能力自备**：任选其一或组合——
  - 模拟器的 **GDB 调试桩**（可用多架构版 GDB 连接，下断点、读寄存器/内存）；
  - 模拟器自带的**调试服务器/调试扩展**；
  - 把上述调试能力封装成 **MCP 工具**，供 AI 直接调用（本仓库不提供该实现）。
- 能读 MIPS 反汇编，认得 `$a0/$a1/$v0` 等寄存器和基本的加载/存储/跳转指令。
- 正版游戏 ISO 自备（法律声明见本仓库 README）。

不需要一次性配齐所有能力：先用存档/帧步进这类零成本手段验证方向，
再决定是否引入调试服务器或 MCP 封装。

一个加分项：PCSX2 的存档文件（`.p2s`）是 ZIP 容器，内含 zstd 压缩的 EE RAM
镜像（32 MB）。解出后可以**离线**读取游戏某一瞬间的内存真值，这等于把
「运行时现场」拍成照片带回家分析，是动态调试的廉价替代。

## 思路与工作流

### 第 1 步：静态分析先打底，列好「要验证的假设」

先离线反汇编，把可疑的**解码 / 装载 / 上传 / 渲染**函数地址找出来，
并为每个地址写下「如果假设成立，这里应该看到什么值」。

例如要验证「错字是不是渲染层读错了字形」：

- 在渲染函数入口，`$a0` 应等于目标字的 tail（行号）；
- 字体对象全局指针 `0x2B23D0` 应等于大字库 ac0_j1 的对象基址；
- 渲染函数返回的位图地址应等于 `位图基址 + tail × 512`。

这些「预期值」就是后面断点命中时的对照基准。

### 第 2 步：用存档槽位复现目标界面

在模拟器里走到目标界面，用**存档槽位**把画面停在现场。
若怀疑问题发生在「渲染进行中」的某一帧，可以先开**帧步进**
（逐帧暂停）把那一帧卡住再存档。

这一步不依赖调试服务器，仅用模拟器自带的帧步进与存档即可完成，
是成本最低的起点。存档既可当场读，也可解出 EE RAM 镜像离线读；
它的价值是把「不确定什么时候发生的现象」变成「一个可反复取样的稳定现场」。

### 第 3 步：下条件断点，收窄命中范围

直接在函数地址下无条件断点，往往会被无关字、无关帧的海量命中淹没。
正确做法是**用条件过滤**，只断感兴趣的那一次。例如：

```
break *0x14dfb0 if $a0 == 847
```

`0x14dfb0` 是 tail→位图的定位函数，`847` 是某个目标字的 tail 值。
这样只有渲染那个字的瞬间才会命中，一次就拿到关键实参。

### 第 4 步：命中后抓寄存器 / 内存 / 纹理

命中后依次取：

- **寄存器**：如 `$a0`（入参）、`$v0`（返回值），判断函数实际算出了什么；
- **内存**：如字体对象头的位图基址 `+0x30`、行字节 `+0x34`、
  当前字体指针 `0x2B23D0`，判断对象是不是你以为的那一个；
- **显存/纹理**：导出 VRAM 或纹理转储，直接看「这个字最后画成了什么」。

三类证据合起来，通常足够判定一条链路里到底哪一环出了问题。

### 第 5 步：与静态分析交叉验证，二分收敛

把实际值对回第 1 步列的预期值：

- 全对 → 这条链路没问题，去查下一条；
- 有一处不符 → 那一处就是分界点，往上/下游继续二分。

静态给出「哪里可疑」，动态给出「那里实际是什么」，两者交替推进。

### 三条互补的动态路线

1. **帧步进 + 存档**：零成本，先试。能把「渲染中」的瞬间卡下来读内存。
2. **条件断点读寄存器**：精确。适合要抓「某一次调用」的入参/返回值。
3. **代码注入 log**：最彻底。在目标函数入口注入一小段 trampoline，
   把关键寄存器写到一个固定空地址，之后照常跑游戏、存档、离线读该地址。
   不需要精确断点，适合断点条件难写或命中太频繁的场合。

**推荐工作流小结**：

1. 存档槽位复现目标界面（必要时帧步进卡帧）；
2. 对解码 / 装载 / 渲染函数下条件断点；
3. 命中后导出寄存器、内存、纹理转储；
4. 与静态预期值对比，二分收敛；
5. 记录结论，并清理残留断点。

## 适用场景

- **静态反汇编到极限**：间接调用、虚函数表、运行时才填充的指针，静态追不动时。
- **字体/渲染链路错位**：静态数据链（编码→区间表→字形表→位图）全对，
  但游戏里就是显示错字，错字只能在渲染瞬间动态抓。
- **CLUT 不明**：颜色查找表运行时生成或乱序，静态反汇编里查不到。
- **「哪个界面走了哪个字库」这类运行时状态**：同一份文本在不同界面可能走不同字库，
  只能读当前字体指针实测。
- **需要确认一次具体的调用**：例如某个函数的入参到底是不是你以为的值。

## 实战案例

以下案例都取自 ACLR 逆向实践中的真实问题，只保留技术路径，省略过程性细节。

### 案例 1：数据链全对却显示错字（「强→刚」）

- **现象**：任务选择界面出现成对系统性错字：强（0x88AA）→刚、击→靶、友→味。
- **静态结果**：编码→区间表→字形表→位图整条数据链全部正确；
  渲染定位函数 `0x14dfb0` 也确实用 `tail × 512` 定位位图。
  静态层面找不到任何能产生这个错字的立足点。
- **静态反证**：三对错字的 tail 差没有规律（+110 / +141 / +13），
  且「友→味」里的「友」是原版就有的字、注入并未改动——排除了「注入错误」
  和「统一 tail 偏移」两种解释。
- **动态关键一步**：存档实测发现，出错界面在存档瞬间的当前字体指针
  `0x2B23D0` 指向的是一个 27 字形的**菜单字体**，而不是大字库 ac0_j1。
  也就是说该界面当时**根本没走那条静态已验证的渲染链**，走了另一条尚未定位的链。
- **结论**：错字不在已知链路内，必须动态抓「渲染那一瞬间」的字体指针和渲染函数实参，
  才能找到真正被使用的那条链。

### 案例 2：TUNE 界面专用小字库与「力」字空白

- **现象**：推进器 TUNE 界面的参数标签里，「力」（0x97CD）数据 100% 正确却渲染空白，
  而「量」（0x97CA）正常——两个码只差 3。
- **静态 + 存档定位**：标签用的既不是大字库 ac0_j1，也不是对话字库 0A93，
  而是 font.bnd 里的一个 **45 字符小字库（ID=9）**；主程序的解码函数
  `0x14dd00` 根本不参与这条路径。
- **动态价值**：这类「数据对却渲染不对」的问题，静态只能证明数据没错，
  无法证明渲染器真的解码了这个码。要靠断点解码函数看该码是否真被解码、
  读字体指针确认当前到底走哪个对象，才能把「解码问题」和「渲染问题」切开。
- **边界**：此码最终未在渲染器侧彻底定位到机制，只能以调整译文措辞绕开。
  可见动态调试能快速收窄范围，但遇到渲染器无规律的行为时仍需留有余地。

### 案例 3：逐像素反推运行时 CLUT

- **现象**：竞技场入场名的字形质量，本地预览和实机画面始终对不上。
- **手段**：拿到模拟器的**纹理转储**（32×32 RGBA 的 PNG），
  与本地存储的 4bpp nibble 字形逐像素对齐，反推出游戏运行时 CLUT 的真实
  `nibble → (RGB, alpha)` 映射。
- **结果**：CLUT 是**乱序**的——白核 nib1 的 alpha 是 128（半透明）而非 255，
  nib3 直接透明，nib2~11 的亮度并不随编号单调变化。
  按真实 CLUT 重新量化字形后，预览与实机从此一致。
- **经验**：CLUT 千万别按「编号越大越亮」的线性直觉脑补，用游戏转储反推才是正解。

### 案例 4：抓上传链的 BITBLTBUF 源/目标地址

- **现象**：上传/渲染链全部静态逆向完后仍有一个矛盾——
  代码里 tail 只决定源位图地址、并不进入 VRAM 目标坐标，
  这与「新增行仍发生字形分裂」的现象直接冲突。
- **手段**：静态挖不到这最后一环，只能动态抓上传：
  对写入 `BITBLTBUF` 的指令下断点，抓它的源地址和目标地址，
  对比「新增行」和「原版行」的差异，即可定位矛盾根源。
- **结论**：有些真相（一次上传实际写了哪里）只存在于运行时，静态代码里根本看不出来。

### 案例 5：断点抓加载/解码链，定位「斜切」发生在哪一步

- **现象**：入场名字体在游戏里看起来被「向右斜切」，但不确定这发生在
  字库加载阶段还是每帧绘制阶段。
- **手段**：把游戏暂停在单字解码函数 `0x255830` 处，从断点往回追调用链，
  得到完整的「单字解码 ← 逐字循环 ← 解压并上传纹理图集 ← 按标志选字库 ←
  字体初始化 ← 界面顶层」加载链。
- **结论**：这条链是**加载时**执行的，不含任何斜切/变换；「向右斜」实际发生在
  每帧绘制阶段，与加载链无关。断点把「静态追虚函数很慢」的问题，
  直接变成了「抓到一条完整调用链」的结论。

## 注意事项

- **工具自备**：GDB 桩、调试服务器、MCP 封装等一律请读者自行获取，
  本仓库不提供下载，也不捆绑任何工具本体。
- **断点条件要收窄**：能按寄存器/内存值过滤就一定要过滤，
  否则海量无关命中会浪费大量来回。
- **大块读内存会被静默截断**：读内存分小步长进行，不要一次读过大范围。
- **断点要清干净**：清断点接口返回的列表结构和直觉可能不符，
  逐条移除后再查询确认，避免残留断点干扰下一轮。
- **装载类函数只触发一次**：字库装载往往只在启动或进入界面时执行一次，
  等游戏跑起来再下断点已经晚了——要先下断点再触发装载，或优先静态/文件分析。
- **抓值要快**：长时间连续跟踪容易让模拟器卡死、trace 中断；
  断点命中后一次取够所需，不要长跑全量 trace。
- **调试接口能力有限**：部分调试接口不提供读 VRAM/GS 的能力，
  此时用「纹理转储」兜底取显存结果。
- **R5900 反汇编要核对**：PS2 的 EE 是 R5900（MIPS 变体），含 MMI/128 位指令，
  通用反汇编器可能误标，别在误标处下结论（见下）。

## 坑与教训

**现象**：静态分析判定渲染函数「不含 tail 乘法」，推导出「两个字应渲染成同一字形」
的矛盾结论。
**根因**：R5900 的三操作数 `MULT rd, rs, rt` 会把低 32 位结果同时写回 GPR `rd`
和 LO；通用反汇编器却把这条指令误标成 nop，导致整条 `tail × 512` 乘法被漏读。
**规避**：对 R5900 的乘法/MMI 指令，以权威 ISA 语义或仿真器源码为准，
不要只看反汇编器的标签。

---

**现象**：读内存返回看似正常，但结果明显缺了一块。
**根因**：一次读太大，被静默截断。
**规避**：按 64 KB（0x10000）小块扫描，不一次读 256 KB（0x40000）级大块。

---

**现象**：清完断点，下次运行断点还在。
**根因**：断点列表接口的字段名与预期不同，清理逻辑没对上。
**规避**：清断点逐个移除，并在下一轮开始前重新查询确认列表为空。

---

**现象**：断点追绘制函数极慢，逐层静态追永远追不完。
**根因**：绘制走大量虚函数表间接调用，表在 BSS 区、运行时才填充。
**规避**：别逐层静态追；直接用断点抓「当前指针/寄存器实值」定位正在用的函数。

---

**现象**：断点下在装载函数上，游戏跑起来后一次都不命中。
**根因**：装载在更早的启动/进界面阶段就执行完了，下断点时已错过。
**规避**：先下断点，再重启或退出重进界面触发装载；或先静态/文件分析确认装载时机。

---

**现象**：预览效果和实机差异巨大，且怎么调都不对。
**根因**：CLUT 乱序——白核 alpha 可能是 128 而非 255，亮度随编号不单调。
**规避**：用游戏纹理转储反推真实 CLUT，再按其 RGB 亮度量化。

---

**现象**：字对、字形对、区间对、CLUT 对，整个字库却错乱/融化。
**根因**：位图/CLUT 未按 **16 字节对齐**（DMA 上传的硬要求）；
区间数 n 与字形数 g 奇偶性不同 → 位图偏移不对齐。
**规避**：改二进制布局先查对齐/边界/奇偶性，再怀疑内容。

---

**现象**：看起来是「A 好、B 好、A+B 坏」的组合触发，被误导成字符组合问题。
**根因**：其实是一个隐藏连续量（如字符数变化使区间数奇偶翻转）在跟着变。
**规避**：把 n / g / 位图偏移 mod16 排成一张对齐表，规律一眼可见。

---

**现象**：反汇编器在 MMI/128 位指令处输出乱码。
**根因**：通用反汇编器按 MIPS32 误标。
**规避**：只在标准 MIPS 指令能可靠反汇编的区域下结论；
关键跳转/乘除用模拟器自带反汇编或人工核对。

以上坑有一个共同点：**调试「工具层」的错误（静默截断、残留断点、指令误标）往往会伪装成
「结论错误」**。排查顺序应当是先排除工具层，再怀疑结论。
