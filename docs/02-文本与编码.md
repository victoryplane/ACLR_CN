# 02 文本与编码：SJIS、MAPPING 码与文本追踪

> ACLR 的文本层并非单一编码：日文原文同时存在自然 SJIS 与 UTF-16LE 对话，汉化还要引入 MAPPING 码。
> 本篇讲清三种编码的差别、容器 id 编号、文本表结构与「从游戏文本反查回写位置」的追踪方法。

## 背景与目标

ACLR（PS2）的可见文本分散在数百个容器里，且编码不一致，拿通用工具直接搜索经常搜不到。
本篇要解决三件事：

1. 说清游戏内并存的编码体系，以及各自如何判定；
2. 说明「容器 id」这套编号，建立「文本 → 容器 → 文件 → 偏移」的定位直觉；
3. 给出 `.mes` 对话表与 SJIS 文本的字节结构，并记录逆向与汉化中踩过的坑。

本篇只覆盖「文本与编码」。解包与压缩见 01，字库与渲染见 03，回写见 04，打包见 05。

## 前置依赖

- 已能从 ISO 解出 AC.BIN，并解析其顶层 BND 条目（见 01-解包.md）。
- 能对 fsliblzs 容器解压，并能解析任务容器内的内层 BND 文件表（见 01-解包.md）。
- 一个能按任意编码读二进制、做偏移定位的脚本环境（Python 3 即可）。
- 十六进制查看/比对工具，用于核对字节与改动。

## 一、编码体系

游戏文本至少有三种编码并存，必须先分清再动手，否则「搜得到、改不对」。

### 1.1 自然 SJIS（日文原文）

大部分非对话文本是标准 Shift-JIS：

- 任务简报 `MissionDataSXX.dat`（任务容器内层 BND 的子文件）
- 任务详情 `missionRemark.bin`
- 菜单文本 `Message.bin` 等

判定与扫描特征：

- 双字节首字节区间 `0x81–0x9F`、`0xE0–0xEF`，次字节 `0x40–0x7E`、`0x80–0xFC`；半角片假名 `0xA1–0xDF`。
- 扫描启发式：遇合法首字节取 2 字节；遇 `0x0A`/`0x0D` 视为换行继续；遇 `0x20`/`0x00` 视为串结束；然后按 shift_jis 解码。

这类文本「字节 = SJIS 码点」，最终字形由该 SJIS 码点在字库中的槽位决定（字库细节见 03）。

### 1.2 对话 UTF-16LE

任务内对话/电台脚本 `sXXX.mes` 不是 SJIS，而是 **UTF-16LE**：

- 每字符 2 字节 `[b0 b1]`，小端值 `(b1<<8)|b0` 即 Unicode 码点：

  ```
  字符 = chr((b1 << 8) | b0)
  ```

- 单字编码示例：`B7 30` = シ（U+30B7）、`FC 30` = ー（U+30FC）、`E9 30` = ラ（U+30E9）；`1F 75` = 生、`53 4F` = 体、`75 51` = 兵、`68 56` = 器。
- 控制码：`0A 00` = 换行（U+000A）；`00 00` = 条目结束（U+0000，不入文本）；`XX FF` = 全角字符 U+FFXX（如 `1A FF` = ：U+FF1A，`01 FF` = ！U+FF01）。
- 说话人行格式：`说话人名 + ：(U+FF1A) + \n + 对话内容`。
- 少数「只有说话人」的条目以单个 `0x0A` 结尾（奇数长度），解码需单独处理，不能套用「两字节一组」的整除假设。

规模参考：343 个任务容器中 328 个含对话，共 6005 行、851 个不同字符，全量解码 0 个替换字符。

### 1.3 MAPPING 码（汉化引入）

汉化后大量中文在原版字库里没有字形，不能直接写自然 SJIS。做法是给该中文字分配一个
**MAPPING 码位**：文本里写这个码，目标字库的对应槽位放该字字形。

- 典型区间 `0x88xx`，例：对 = `0x88BB`。
- 本质是「码位 → 扩展字库字形槽」的显式映射，落在 SJIS 兼容码位空间内（字库按区间表查码位）。
- 除 `0x88xx` 外也使用其它空闲 SJIS 码位做映射（如重定位到 `0x9457`、`0x974B`、`0x955F` 等）。

关键约束：MAPPING 码位必须选「全语料都不出现」的空位，否则会与原文或其它界面撞码（见坑 5.2）。

### 1.4 输出编码由目标字库决定

同一条译文写回时用什么编码，取决于它最终由哪个字库渲染：

| 渲染路径 | 字库索引方式 | 文本输出编码 |
|---|---|---|
| 菜单/属性页（ac0_j1 扩字） | SJIS 码点 + MAPPING 槽 | MAPPING 码（`0x88xx` 等） |
| 对话（0A93 Unicode 字库） | Unicode 码点 | Unicode 码点（UTF-16LE） |
| 未扩字的自然日文文本 | 原版 SJIS 字形 | 自然 SJIS |

同一字在不同界面可能要用不同编码；「翻译输出用哪个字库，就用哪种编码」。先确认渲染字库再定编码，
否则显示错字或空白（见坑 5.3）。

## 二、容器 id 与文本归属

AC.BIN 顶层是一个 BND 归档，每个条目用数字 id 标识，这就是「容器 id」。文本定位的第一步就是
按内容类别找到对应容器 id：

| 容器 id | 内容 |
|---|---|
| `0x2000–0x8000` | 外层任务容器（343 个）；内层 BND 含 `.mes` 对话与 `MissionDataSXX.dat` 简报 |
| `0x3A0` / `0x3A7` / `0x3A8` | 竞技场文本 |
| `0x3A1` | 任务详情 missionRemark |
| `0x3A2` / `0x3A9` | 战况报告（mission） |
| `0x3A4` / `0x3A5` / `0x3A6` | 渡鸦名单 RankerInfo / RankerInfo2 / RavenInfo |
| `0x432` / `0x433` | 系统消息 dialog.fmg / linehelp.fmg |
| `0x436` | 部件介绍 new_AllParts.bin |
| `0x043C–0x043F` | 属性/TUNE 帮助 asm_disp |
| `0x0335` / `0x0439` | 按键提示 keyguide |
| `0x001A` / `0x0A90` | 任务内界面消息 |
| `0x0AE–0x0FB` / `0x1EC–0x234` | 请求邮件 / 战况报告 |

外层任务容器是嵌套结构：id 指向的数据块先经 fsliblzs 解压，解压后以 BND 魔数开头，再解析内层
BND 文件表得到子文件。子文件按内层 id 区分：对话 `.mes` 为内层 id=3，简报 `MissionDataSXX.dat`
为内层 id=6。

## 三、文本表 / 消息表结构

### 3.1 .mes 对话表

以任务 001 的 `sXXX.mes` 为样本推得的布局（不同任务结构可能略有差异，需自行实测）：

- `0x00`：u32 条目数 `count`。
- `0x04`：头部配置区（变长）。
- `0x10` 起：`count` 条 16 字节条目，其中 `+0x0C` 处是一个指针，指向二级指针表。
- 二级指针表：每项 8 字节 = `[文本指针][00 00 00 00]`，文本指针指向正文。
- 正文：UTF-16LE 字符串，以 `00 00` 结束。

解码顺序：读 `count` → 逐条取 `+0x0C` 指针 → 跳到二级指针表取文本指针 → 从文本指针按 `00 00`
边界读 UTF-16LE。

### 3.2 SJIS 文本（简报 / 说明）

简报 `MissionDataSXX.dat`、`missionRemark.bin` 走自然 SJIS，没有 `.mes` 那种指针表，按
「字符串扫描 + SJIS 解码」直接提取字段（地点 / 任务名 / 势力 / 正文 / 时间等）。各字段的偏移与
长度需在具体容器内自行实测对齐。

### 3.3 表现层：换行符 ⏎ 与行宽（→ 03/04）

文本中的换行控制码在翻译工作流里统一记作 **⏎**（U+23CE），它只是「换行」的标记，不进入字库字符集；
实际字节在 SJIS 里是 `0x0A`，在对话 UTF-16LE 里是 `0A 00`。

对话行宽有硬约束：**每行 ≤ 20 全角字**。断句规则：行尾不挂结构词（的/着/得/也/还/把/被…）、
行首不出现「的/地/得」碎片、能合并就合并、行数不必与日文对齐。宽窄与渲染、回写细节分别见
03-字库与渲染.md、04-回写与压缩.md。

## 四、文本追踪方法论

从「游戏里看到一句话」到「改哪里的哪个字节」的通用流程：

1. **判类别**：先判断这句话属于对话 / 简报 / 竞技场 / 系统消息 / 菜单 / 部件 / 任务详情 / 邮件 /
   报告 / 名单 / 界面消息等哪一类。
2. **定容器**：按类别查容器 id（见上表）；若是任务文本，进一步定位外层任务容器 id（`0x2000–0x8000` 区间）。
3. **解压 + 内层定位**：任务容器先 fsliblzs 解压，再解析内层 BND 拿到子文件与偏移。
4. **编码定位**：按编码特征在子文件内定位目标串的字节范围——SJIS 用首字节扫描，UTF-16LE 按
   2 字节码点解码后匹配。
5. **唯一性确认**：同一句话可能出现在多个容器/副本；用「字符串 + 周围上下文 + 容器」三方确认，
   避免改错副本。
6. **记录回写位置**：登记「容器 id → 内层文件 → 文件内偏移 → 长度」，回写脚本据此做等长/变长替换
   （规则见 04）。

核心产物是一张「文本 → 位置」五列表：**类别 / 容器 id / 源文件 / 译文 / 回写脚本**，所有文本改动的
定位都以这张表为准，改动后也要回填这张表。

## 五、坑与教训

### 5.1 把对话码当「自定义 SJIS」找转换表

- 现象：对话码点含大量无效 SJIS 首字节，反复找「对话码→SJIS」转换表都找不到。
- 根因：对话码本就是 Unicode（UTF-16LE），不存在转换表。
- 规避：先用已知字符验证码点（按小端读一段对话字节，看是否拼出预期的片假名/汉字），不要预设
  「一定有自定义映射表」。

### 5.2 MAPPING 码撞码（希腊字母被占）

- 现象：把某些中文字分配到 `0x83xx` 码位后，菜单/UI 里的希腊字母变成中文错字。
- 根因：`0x839F`=Α、`0x83A0`=Β、`0x83B5`=Ψ 等码位在菜单/UI 实际使用中；只扫了部分语料就误判为「空闲」。
- 规避：空闲码位判定必须扫描全语料（所有文本来源），看似空闲的 `0x83xx` 区间可能已有用途；确认后再
  落码，落码后还要全文核对原用途是否受影响。

### 5.3 编码与字库不匹配 → 错字/空白

- 现象：译文写回后显示错字、缺字或整段空白；「左边缺字 + 剩余文字左对齐」。
- 根因：同一界面有独立渲染字库（属性页走 MAPPING 码、TUNE 标签走 ID=9 小字库、帮助文本走 ac0_j1
  大字库），编码写成了别的字库的码位，或目标字库没补对应字形。
- 规避：先确认目标界面的渲染字库与索引方式，再决定输出编码；新增字要在对应字库补字形（见 03）。

### 5.4 单字节 00 误当分隔符

- 现象：早期对话提取把「最」（U+6700）等 U+XX00 类字符解析错。
- 根因：把单字节 `0x00` 当行分隔符，而 UTF-16LE 的 U+XX00 字符低字节就是 `0x00`，被误切。
- 规避：直接按原始字节以 `00 00` 双零为边界读 UTF-16LE，不要按单字节 `0x00` 切分。

### 5.5 个别字渲染空白（数据全对仍空白）

- 现象：TUNE 界面某字（如「力」，码位 `0x97CD`）字形数据字节级正确，却始终渲染空白。
- 根因：渲染器对该码/字形槽组合存在未解 bug，与数据无关。
- 规避：这类渲染 bug 不必死磕，用改写译法绕开该字；是否绕得开需按具体界面实测。渲染链分析见
  03-字库与渲染.md。
